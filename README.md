# Paragliding forecast Telegram bot

Командный Telegram-бот: лётный прогноз для параплана по сохранённым стартам —
разбор текстом + PNG-графики. Данные берутся из **open-meteo** (факты), а
**разбор — вердикт, лётное окно, риски, лучший день — делает Gemini** по этим
реальным числам, не выдумывая их. Без ключа Gemini бот работает на встроенных
детерминированных правилах (`engine.py`).

```
Telegram → bot.py → forecast.py → open-meteo (факты)
                                    ├── Pillow  → графики (визуализация фактов)
                                    └── Gemini  → анализ   (fallback: правила engine.py)
```

## Команды

| Команда | Что делает |
|---|---|
| `/today [старт]` | подробный прогноз на сегодня (+3 графика) |
| `/tomorrow [старт]` | подробный прогноз на завтра |
| `/threedays [старт]` | обзор на 3 дня (+бар-график) |
| `/week [старт]` | обзор на неделю |
| `/twoweeks [старт]` | обзор на 2 недели |
| `/scan` | лётные дни на неделю по всем сохранённым стартам; под сводкой — кнопки «старт + день» → подробный прогноз на 1 день |
| `/forecast <старт> <диапазон>` | вручную: `1d · 3d · week · 2weeks` |
| `/route [дата] [ЧЧ:ММ]` | погода по маршруту: список координат в сообщении или GPX-файл |
| `/settings` | средняя маршрутная скорость и учёт ветра во времени прилёта |
| `/model [auto\|ecmwf\|gfs\|icon]` | выбор метеомодели (деф. Auto); без аргумента — кнопки-пикер. **Единственный** способ сменить модель насовсем: кнопка под прогнозом пересчитывает разово |
| `/sites` · `/help` | список стартов · справка |

Если старт не указан, а он один — берётся автоматически. Список команд виден в
меню Telegram (ставится на старте через `set_my_commands`).

После прогноза на день (`/today`, `/tomorrow`, выбор дня из обзора) доступна
кнопка **🌬 Ветер по высотам** — PNG-таблица: строки высоты × столбцы часы,
в ячейке стрелка (куда дует) и скорость, цвет — сила ветра.

## Погода по маршруту

`/route` принимает маршрут **текстом** (по точке на строку, `широта, долгота[, имя]`;
понимает десятичную запятую, вставку из Google Maps и градусы-минуты-секунды),
**GPX-файлом** (`<rte>` → `<trk>` → `<wpt>`, трек прореживается) или **KML-файлом**
(`<LineString>` → `<Point>` → любые `<coordinates>`). Минимум 2 точки, максимум 50.

В KML координаты записаны как `долгота,широта` — наоборот против GPX; бот это
учитывает. KMZ не поддерживается: это архив, его надо распаковать.

```
/route завтра 11:30
42.4776, 44.4787, Гудаури старт
42.2104, 44.6890, Пасанаури
```

Что происходит дальше: маршрут режется на сэмплы с шагом 10 км (разрешение глобальных
моделей — точки чаще сетки дают ложную детализацию), поворотные точки включаются
принудительно. Рельеф берётся отдельным запросом к Elevation API (Copernicus DEM
GLO-90) с шагом 1 км, погода — **одним** мульти-точечным запросом. Время прибытия в
каждую точку считается маршем вперёд с учётом ветра: `GS = V·cos(WCA) + попутная
составляющая`, снизу ограничено 8 км/ч. Рядом показывается время без учёта ветра —
если расхождение больше 20 минут, это отдельная строка предупреждения.

В карточке — километр, время прибытия, составляющая ветра вдоль курса, абсолютный
ветер на рабочей высоте и оценка силы потоков. Осадки и грозы выносятся строками с
указанием километра и часа. Высоты (база, рабочий диапазон) считаются и участвуют в
дальнейшей оценке, но в таблицу не выводятся.

Знаки заданы один раз и соблюдаются везде: `wind_along = −V·cos(θ − φ)`,
`wind_cross = −V·sin(θ − φ)`, где θ — направление, откуда дует, φ — пеленг курса.
Положительная составляющая вдоль — попутный ветер, положительная поперёк — снос вправо.

`/settings` задаёт среднюю маршрутную скорость (10–45 км/ч, по умолчанию 25 — это
средняя по маршруту с учётом наборов в термиках, а не скорость крыла) и тумблер учёта
ветра. Настройки личные — у каждого пилота свои, как и постоянный выбор метеомодели.

### Кнопки под карточкой

- **характерные точки** — старт, поворотные, вершины рельефа, узкое место, точка
  обрыва, финиш (не больше восьми). Открывают подробности одной точки: ветер вдоль и
  поперёк курса, база, рельеф, рабочий коридор, запас времени и три субоценки, которые
  тянут балл вниз. Высоты здесь есть — за ними сюда и приходят.
- **📈 Разрез** — картинка вдоль маршрута: рельеф по мелкой сетке, безопасная высота
  (рельеф + 300 м), рабочий коридор между ней и меньшей из двух верхних линий, потолок
  термиков и база облаков, стрелки ветра, время прилёта и лента лётности. Где коридор
  схлопывается — красная зона: это то, чего в числах не видно.
- **🤖 Разбор** — интерпретация от Gemini. Модель получает уже посчитанные числа и
  пишет только текст: балл, категорию, статус и время прилёта у неё не запрашивают,
  поэтому переврать их она не может.
- **🕐 Другое время** — пересчёт на любое время вылета из скана.

Разрез, детали точки и другое время не стоят ни одного нового запроса к open-meteo:
под кнопкой лежит исходный запрос, а погода берётся из кэша.

Рельеф не загрузился → разреза нет, и кнопка говорит об этом прямо: разрез без
рельефа — пустая рамка.

### Проверка ответа модели

Комментарий, привязанный к километру, которого нет в расчёте, выбрасывается: модели
свойственно схлопывать соседние точки или добавлять промежуточную.

Комментарий, в котором знак ветра перевёрнут — «попутный» при встречном или наоборот, —
до пилота не доходит. Это самая частая содержательная ошибка на маршрутных данных, и
совет, противоположный правильному, опаснее отсутствия совета.

Чего проверки не ловят: сводка не привязана к точке, и перевёрнутый знак в ней поймать
нечем — «встречный на второй половине» бывает верно при попутном на первой.

### Сохранённые маршруты

- `/saveroute <имя>` — сохранить последний посчитанный маршрут. Хранится только
  геометрия: погода всегда считается заново, устаревать нечему.
- `/routes` — список с длиной и числом точек, у каждого кнопка «посчитать».
- `/delroute <имя>` — удалить.
- `/route <имя> завтра 11:30` — посчитать сохранённый маршрут. Имя может быть из
  нескольких слов.

Маршруты — личные: хранятся в БД по `user_id`, потолок — 20 маршрутов на пилота
(`store.MAX_ROUTES`).

### Как оценивается маршрут

**Три профиля критериев**, потому что у точки в воздухе нет склона. Профиль *старта* —
это в точности та же оценка, что у `/today`. Профиль *маршрута* выбрасывает направление
к склону и приземные порывы, а их место занимают ветер вдоль курса (вес 0,20), рабочий
диапазон высот (0,16), увеличенный вес гроз (0,16), абсолютный ветер на рабочей высоте
(0,10) и снос поперёк курса (0,04). Профиль *финиша* — это старт без направления к
склону: приземный ветер и порывы там снова важны, потому что это посадка.

Шкала ветра вдоль курса асимметрична намеренно: попутные +8…+20 км/ч — идеал, а
встречные −15 и сильнее — уже нелётно. Сильный попутный это подарок, сильный встречный
растягивает маршрут и закрывает окно раньше, чем ты долетишь.

**Три маршрутных вето** в дополнение к тринадцати существующим: база ниже безопасной
высоты над рельефом, эффективная путевая ≤ 8 км/ч и прилёт после закрытия термического
окна. Вето на участке **не обнуляет маршрут** — оно переводит его в состояние
«обрывается на N-м км». Знать, что 60 км из 80 проходятся отлично, важнее, чем получить
ноль: маршрут тогда перекраивают, а не отменяют день.

**Балл маршрута** = 0,6 × худшая точка + 0,4 × среднее, взвешенное по длинам участков.
Маршрут рвётся по слабому звену, но одна плохая точка не должна обнулять хороший день.
Выше балла стоит **статус выполнимости**: проходится · обрывается на N-м км · не
успеваешь · данных не хватает.

**Три вещи считаются по уже загруженным данным, без единого нового запроса:**

- *Гроза впереди по курсу* — для каждой точки проверяются грозовые вето в точках на
  60 км вперёд, каждая в своё время прилёта. На старте гроза в 60 км не твоя проблема,
  на 40-м километре — твоя.
- *Скан времени вылета* — шаг 30 минут по термическому окну первой точки. Если ни одно
  время не даёт проходимый маршрут, так и пишется: показать «лучший из непроходимых»
  значит предложить выбрать, каким способом не долететь.
- *Обратное направление* — те же точки в обратном порядке. При устойчивом ветре разница
  между «туда» и «обратно» часто оказывается разницей между несостоявшимся и рекордным
  днём.

**Чего пока нет** (следующая часть): PNG-разрез вдоль маршрута, карточка отдельной
точки, сохранённые маршруты и ИИ-разбор.

**Метеомодель.** Источник open-meteo (`&models=`): `auto` (`best_match`), `ecmwf`,
`gfs`, `icon`. По умолчанию — **Auto**. Постоянную модель меняет только команда
`/model` (без аргумента — кнопки-пикер). Кнопки «🌐 Другая модель» под прогнозом
пересчитывают **разово**: личная постоянная настройка пилота не трогается, а разовый
выбор распространяется на все кнопки того же сообщения — ИИ-разбор и ветер по высотам
считаются по той модели, что показана в карточке. Текущая модель подписана в карточке.

**Потолок термиков всегда считается по GFS**, независимо от выбранной модели.
Отдельный узкий запрос за `boundary_layer_height` идёт конкурентно с основным, и
серия подставляется в ответ по индексу (массивы часов у open-meteo совпадают
между моделями). Причин две: у ECMWF и ICON этой серии нет вовсе, а под `auto`
её отдаёт неизвестно какая подложка `best_match` — число оказывается несравнимым
между стартами и днями. Когда выбрана сама GFS, второго запроса нет. Если
побочный запрос не удался, потолок считается по выбранной модели, то есть на
ECMWF и ICON его по-прежнему не будет. В карточке это подписано явно:
`· ECMWF (потолок GFS)`.

Из GFS берётся ровно одна переменная. Заполнять ей остальные пробелы значило бы
подменить чужой моделью половину входов скоринга — тогда выбор ECMWF теряет смысл.

Почему Auto, а не ECMWF (проверено живыми запросами по координатам старта):

| Поле | ecmwf | icon | gfs | auto |
|---|---|---|---|---|
| `cape`, радиация, влажность, T на 850/700 | ✅ | ✅ | ✅ | ✅ |
| `convective_inhibition` | ❌ | ✅ | ✅ | ✅ |
| `visibility`, ветер на 80/120 м, 950 гПа | ❌ | ✅ | ✅ | ✅ |
| `lifted_index` | ❌ | ❌ | ✅ | ✅ |
| `boundary_layer_height` (потолок термиков) | ❌ | ❌ | ✅ | ✅ |

На ECMWF выпадают сдвиг ветра, видимость, LI и CIN — это **4 вето из 13 не могут
сработать в принципе** (`cape_cin`, `lifted_index`, `visibility`, `shear`). W\* и
глубина рабочего слоя работают везде: пограничный слой всегда берётся из GFS
(см. выше), а радиация есть у всех моделей. Скоринг честно деградирует (веса
перенормируются, непроверенные вето перечисляются словами в карточке), но дефолт
должен считать всё. Молний у open-meteo для Кавказа нет ни на одной модели:
`lightning_potential` и `thunderstorm_probability` существуют только для ICON-D2
в Центральной Европе.

## Как считается лётность

Пороги живут в одном месте — `criteria.py`, и оттуда же берутся карточкой,
графиками и промптом для Gemini. Калибровка — **уверенный XC-пилот на Niviuk
Ikuma 3 P** (trim ≈10,6 м/с ≈ 38 км/ч), не новичок.

```
значение параметра → уровень (бэнд) → субоценка 0–100
  → свёртка по группе (худший / средний) → веса групп → взвешенная сумма
  → мультипликативные штрафы → потолок по лимит-фактору → вето → категория
```

18 параметров в 10 группах: ветер у земли и на 925/850 гПа (0,22), порывы (0,15),
направление к склону (0,12), термичка — W\*, глубина слоя, Thermal Index (0,15),
неустойчивость — CAPE и Lifted Index (0,12), облачность и запас под базой (0,08),
осадки и видимость (0,06), сдвиг ветра 0–100 м (0,06), стратификация (0,02),
длительность окна (0,02).

Категории: 🟢🟢 идеальная (85+) · 🟢 отличная (70+) · 🟡 удовлетворительная (55+)
· 🟠 маргинальная (40+) · 🔴 нелётная (15+) · ⛔ опасная. Любое из 13 вето
(дождь в час, CAPE при снятой крышке, подветер, ветер ≥ trim, порывистость >1,7×,
видимость <1,5 км, сдвиг >6,9 м/с и т.д.) обнуляет балл независимо от суммы.

**Пропуски данных обрабатываются явно.** Параметр без данных не оценивается, веса
перенормируются, а вето, входы которого неизвестны, **не срабатывает** и попадает
в «не проверено вето» — эта строка есть в карточке, потому что молчаливая
деградация опаснее всего: «нет данных по видимости» не должно выглядеть как
«с видимостью всё хорошо».

Три места, где документ не даёт правила, решены явными константами в `criteria.py`
(там же объяснено почему): опорный ветер для отношения порыв/ветер, потолок
категории при неполных данных и потолок по лимитирующему фактору — без последнего
девять хороших групп перевешивали одну нелётную, и ветер под 50° к склону давал
«идеальный день».

Чего посчитать нельзя — и что вместо этого: фён по правилу Шамони требует
перепада давления через хребет, то есть двух точек по разные стороны, поэтому
остаётся **эвристическим предупреждением**, а не вето; W\* — **оценка** по
радиации и глубине слоя (у open-meteo нет потока тепла), везде помечена как
оценка; вето «база ниже вершин маршрута» работает, только если у старта задано
необязательное поле `route_top_m`.

## Доступ и защита API

- **Whitelist** — `ALLOWED_USER_IDS=123456789,987654321` в `.env` (Telegram user ID
  через запятую). Пусто — бот открыт всем, в лог пишется предупреждение.
  Чужому пользователю бот отвечает отказом и показывает его ID — удобно
  пересылать владельцу для добавления.
- **Кулдаун** — не чаще одного прогноза в `COOLDOWN_SEC` секунд на пользователя
  (по умолчанию 10) и не более одного одновременного запроса от пользователя.
- **Кэш** — готовые прогнозы (текст + PNG) живут в памяти `CACHE_TTL_MIN` минут
  (по умолчанию 15): повторный запрос того же старта/диапазона не тратит
  квоты open-meteo и Gemini.

## Что нужно

- **Токен бота** — у [@BotFather](https://t.me/BotFather): `/newbot`.
- **Ключ Gemini** (бесплатный) — https://aistudio.google.com/apikey. Нужен для
  анализа; без него включается встроенный разбор на правилах.
- Docker **или** Python 3.11+ — точка входа `app.py` держит бота и API одним
  процессом через `asyncio.TaskGroup` (появился в 3.11); на более старой
  версии это упадёт неочевидным `AttributeError` вместо внятного сообщения.

## Раскатка — вариант A: Docker (рекомендую)

```bash
cd paragliding-bot
cp .env.example .env          # впиши BOT_TOKEN и GEMINI_API_KEY
docker compose up -d --build
docker compose logs -f
```

- Шрифты (кириллица для графиков) и `tzdata` ставятся в образ автоматически.
- Данные лежат в SQLite в именованном volume `pgbot-data` (`/app/data/pgbot.db`),
  которым владеет пользователь контейнера — поэтому `/add`, `/removesite`,
  `/saveroute` и `/settings` могут писать. Старты — общая библиотека на всех
  пользователей бота; маршруты, маршрутные настройки и выбор модели — личные,
  по `user_id`. При первом старте на пустой библиотеке старты сидируются из
  встроенного `sites.json`.
  Правка вручную: `docker compose exec pgbot sqlite3 /app/data/pgbot.db` (или
  через сам бот командами `/add` · `/removesite`).
- **Обновление с версии на JSON-файлах.** Если в томе остались старые
  `sites.json` / `routes.json` / `settings.json` / `model.json`, бот переносит
  их в БД сам на первом старте и переименовывает в `*.migrated` — не удаляет,
  это и есть путь отката. Маршруты, настройки и модель раздаются только тем,
  кто на момент этого старта перечислен в `ALLOWED_USER_IDS`: раздавать личные
  данные больше некому. При пустом списке (открытый режим) эти три файла
  остаются на диске непереименованными, и миграцию можно повторить позже,
  когда список появится. Старые файлы ищутся и в каталоге БД, и в корне
  репозитория — на systemd-пути они лежали именно там. Записи, которые перенести
  не удалось (битые координаты, неизвестная модель, нечисловая скорость), в БД не
  попадают, но перечисляются в логе строкой `МИГРАЦИЯ ПРОПУСТИЛА N ЗАПИСЕЙ`;
  сами данные остаются в `*.migrated`.
- Часовой пояс — переменная `TZ` (по умолчанию `Asia/Tbilisi`), от неё зависит,
  какой день считается «сегодня/завтра». Задать: `TZ=Europe/Moscow` в `.env`.
- Логи ротируются (10 МБ × 3).

Обновление: `git pull && docker compose up -d --build`.

### Caddy: домен, TLS и мини-приложение (фаза 3)

- Переменные в `.env`: `PUBLIC_DOMAIN` (домен, который позже пропишете в
  BotFather на фазе 5), `TLS_CERT_DIR` (каталог со своим сертификатом — внутри
  ожидаются `fullchain.pem` и `privkey.pem`), `API_PORT` (порт uvicorn внутри
  сети compose; наружу не публикуется — в интернет смотрит только Caddy).
- `docker compose up -d` поднимает **два** контейнера: `pgbot` (бот + API,
  порт виден только внутри сети compose) и `caddy` (порты 80/443 наружу, TLS,
  отдача статики, реверс-прокси `/api/*` на `pgbot:8080`).
- Проверка живости: `curl -s https://$PUBLIC_DOMAIN/api/health` должен
  вернуть число стартов в поле `sites` — пустая база почти всегда означает,
  что том `pgbot-data` не примонтирован.
- Проверка подписи: временно повесить Web App-кнопку на этот домен через
  BotFather и открыть `/` в клиенте Telegram — страница `static/index.html`
  спросит `/api/prefs` с подписанной `initData` и напишет «Подпись принята,
  HTTP 200» (или код отказа, если подпись не сошлась).
- Автоматический Let's Encrypt вместо своего сертификата: удалить в
  `Caddyfile` строку `tls /certs/fullchain.pem /certs/privkey.pem` целиком —
  остальное менять не нужно, Caddy сам выпустит сертификат на `PUBLIC_DOMAIN`.
- `static/` — однофайловая заглушка ровно для проверки подписи живым
  клиентом Telegram; настоящий интерфейс (`webapp/`) появится на фазе 4, и
  `./static:/srv/www` в `docker-compose.yml` тогда сменится на
  `./webapp/dist:/srv/www`.

## Раскатка — вариант B: systemd + venv (bare metal / VPS)

```bash
cd paragliding-bot
./deploy.sh            # venv, зависимости, проверка шрифтов, рендер unit-файла
# затем по подсказке скрипта:
#   отредактировать .env (BOT_TOKEN)
sudo cp deploy/pgbot.service /etc/systemd/system/pgbot.service
sudo systemctl daemon-reload && sudo systemctl enable --now pgbot
journalctl -u pgbot -f
```

`deploy.sh` сам подставит в unit-файл текущий путь, пользователя и python из venv.

> ⚠️ **Мини-приложение здесь без Caddy.** Рендерящийся юнит-файл запускает
> `bot.py` — только чат, без HTTP: Caddy и TLS в этом плане покрывают лишь
> Docker-раскатку (вариант A). Чтобы поднять и API, замените в
> `deploy/pgbot.service` после рендера `bot.py` на `app.py` (тот же
> объединённый процесс, что и в Docker). Делайте это осознанно: перед
> процессом здесь никто не стоит, `app.py` слушает `API_HOST = 127.0.0.1`, и
> без собственного реверс-прокси мини-приложение снаружи сервера всё равно
> недоступно — доступен останется только чат через polling.

> ⚠️ **Шрифты для графиков.** На Linux нужен кириллический TTF, иначе подписи на
> PNG будут «квадратиками» или мелким дефолтом. Docker ставит `fonts-dejavu-core`
> сам; для bare-metal: `sudo apt-get install -y fonts-dejavu-core`. `charts.py`
> ищет DejaVu / Liberation / Arial по стандартным путям.

## Добавить старт

Прямо из Telegram: `/add <Имя> <lat> <lon> <экспозиция>` (или `/add` — бот
спросит по шагам) · удалить: `/removesite <Имя>`. Старты — общая библиотека,
видна всем пользователям бота. Правки сохраняются в БД (volume `pgbot-data`
в Docker) и переживают перезапуск/пересборку.

Вручную (bare-metal / dev): открой БД напрямую — `sqlite3 data/pgbot.db`,
таблицы `sites` (`name`, `lat`, `lon`, `elevation_m`, `aspect`, `aspect_deg`,
`slope_deg`, ...) и `site_aliases`. Путь к БД переопределяется переменной
`DB_PATH` (по умолчанию `data/pgbot.db` рядом с кодом; в Docker —
`/app/data/pgbot.db`).

## Структура

```
bot.py            aiogram-обработчики команд + меню
guards.py         whitelist (ALLOWED_USER_IDS) + кулдаун запросов на пользователя
route.py          маршрут: разбор текста и GPX, геометрия, время прилёта, карточка
store.py          SQLite: старты (общая библиотека), маршруты/настройки/модель
                  (личные, по user_id), миграция с JSON на первом старте
forecast.py       резолв старта → open-meteo → факты + графики → анализ (Gemini/правила)
analysis.py       Gemini: разбор реальных данных в лётную оценку (текст для Telegram)
criteria.py       ЕДИНСТВЕННЫЙ источник порогов: бэнды, веса, вето, скоринг 0–100
engine.py         запрос, производные метрики, факты (facts_*), карточки (report_*)
charts.py         PNG, светлая тема, м/с, кроссплатформенные шрифты
sites.json        затравка библиотеки стартов при пустой БД (сидируется один раз)
Dockerfile · docker-compose.yml · .dockerignore
deploy.sh · deploy/pgbot.service.tmpl · Makefile
requirements.txt · .env.example
```

## Заметки

- **LLM объясняет скоринг, а не пересчитывает его.** Детерминированный расчёт
  (`criteria.py`) — источник истины; Gemini получает готовый балл, категорию,
  лимитирующий фактор и список вето и переводит это на человеческий язык.
  Переопределять вето он не вправе. Блок порогов в промпте **генерируется** из
  `criteria.reference_text()` — раньше он был переписан в промпте руками и молча
  расходился с расчётом при каждой правке (на это есть тест). Если Gemini
  недоступен — показывается детерминированный разбор.
- **Атрибуция.** Данные open-meteo под CC BY 4.0, ссылка проставляется в карточке.
- **Термическое окно считается локально по геометрии солнца** (`engine.sun_hours`):
  на каждый дневной час — азимут и высота солнца плюс `slope_sun_index` (0–1,
  насколько прямо солнце бьёт в склон старта с учётом `aspect_deg`). Отсюда
  `thermal_window` — start/peak/end. Промпт требует разбирать и выносить риски
  только внутри окна: иначе LLM комментирует ветер в 06:00, когда термички ещё нет,
  и не видит, что вечером солнце уходит со склона. По этому же окну считается
  «⏱️ Лётное окно» в карточке и полоса на метеограмме — раньше они растягивались
  на всё светлое время. Крутизна склона берётся из необязательного поля `slope_deg`
  старта (по умолчанию 25°).
- Windy **не** используется — его бесплатный ключ отдаёт перемешанный demo-шум
  (вот это и есть пример «LLM/сервис выдумывает числа» — так нельзя).
- Сеть нужна для open-meteo и Gemini; на сервере она открыта (ограничение `curl`
  было лишь в песочнице Claude Code).
- Движок общий со скиллом; при желании — вынести в отдельный пакет.
