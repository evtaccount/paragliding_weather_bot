# Решения: перенос системы критериев XC в бота

Ветка `feature/xc-criteria`. Источник требований — исследовательский документ
о критериях погоды для горных полётов (калибровка под уверенного XC-пилота на
Niviuk Ikuma 3 P, trim ≈38 км/ч).

## Заданы пользователем

1. Пороги — из документа, а не прежние консервативные (было: >7 м/с уже нелётно).
2. Скоринг — полный почасовой: субоценки → веса → штрафы → вето → категория.
3. Балл дня — среднее по часам термического окна.
4. Модель по умолчанию — Auto (`best_match`).
5. В карточке — полоса по часам.
6. Нау-каст — только радар RainViewer, и сначала проверить покрытие.

## Приняты по ходу (документ правила не даёт)

Все живут именованными константами в `criteria.py` — чтобы их было видно и легко
поменять, а не искать по коду.

### Опорный ветер для отношения порыв/ветер — `GUST_FACTOR_REF_WIND_MS = 6.1`
Правило «порывы >1,5× среднего» подразумевает соизмеримый средний ветер; при
штиле оно вырождается. Знаменатель ограничен снизу верхней границей «отличного»
диапазона у земли.

Проверено на живых данных, а не на фикстурах: без ограничения ветер 2,1 м/с с
порывом 5,6 (обычный рабочий термический час) получал «фактор 2,62» и прямое
вето; при ограничении на 4,2 ветер 4 м/с с порывом 7 (14→25 км/ч) получал
«нелётно» по группе порывов и топил весь день до маргинального. На 6,1 шкала
ведёт себя разумно на всём диапазоне 2–9 м/с, а настоящий порыв-фронт
(6 м/с → 11) вето по-прежнему получает. При слабом ветре рваность меряет
абсолютный отрыв — он в той же группе и сворачивается по худшему.

### Потолок по лимитирующему фактору — `LIMIT_CAP_MIN_WEIGHT = 0.06`
Взвешенная сумма по десяти группам сама по себе слишком снисходительна: если
девять групп идеальны, десятая не сдвинет балл ниже ~85, даже когда она
«нелётная». Ветер под 50° к склону давал «идеальный день» — так нельзя.

Документ называет лимитирующий фактор («то, что тянет день вниз»), но в формуле
его не использует. Здесь он и применяется: итоговый балл не выше, чем на один
уровень над худшей значимой группой. Группы весом 0,02 (стратификация,
длительность окна) в потолок не входят — документ сам объявил их
второстепенными, давать им право обрушить оценку было бы противоречием.

### Потолок при неполных данных — `MIN_CONFIDENCE = 0.6`
Нельзя объявить идеальный день, не проверив треть критериев. Категория
ограничивается «удовлетворительной» + предупреждение.

### CIN без своей шкалы
Низкий CIN при низком CAPE — нормальный день; оценка CIN в отрыве давала бы
постоянную ложную тревогу. Он работает только во взаимном вето (CAPE>1500 при
CIN<25) и в ограничении группы «грозы», когда CIN неизвестен: вето не
срабатывает (правило документа о пропусках), но зелёную группу рисовать нельзя.

### Свёртка внутри группы
`min` для ветра, порывов, направления, гроз, облачности, осадков и сдвига —
там решает худший параметр. `mean` для термички и стратификации — там важна
общая картина, а не одно число.

### confidence считает параметры, а не группы
Группа «грозы» выживает на одном CAPE без Lifted Index. Для СЧЁТА она берётся
целиком (вносит свой вес по тому, что есть), но строка «критериев посчитано»
уменьшает её вес на долю пришедших параметров — иначе показывала бы 100% при
половине отсутствующих параметров.

### Границы бэндов
Интервалы полуоткрытые `[lo, hi)`. Одно правило на всю таблицу, проверяется
структурным тестом (нет разрывов и наложений, ось покрыта целиком).

## Что посчитать нельзя — и что вместо этого

- **Фён по правилу Шамони** (перепад давления через хребет >4 гПа) требует двух
  точек по разные стороны хребта; у бота точечные данные, кольцо ±0,05° в
  `_detail_context` — это ~5,5 км, не хребет. → эвристическое ПРЕДУПРЕЖДЕНИЕ по
  косвенным приметам, не вето. В карточке и промпте помечено как эвристика.
- **«База ниже старта»** — LCL считается по T/Td самого старта и по построению
  никогда не окажется ниже него. Настоящая проверка — против вершин маршрута,
  которых бот не знает. → бэнд «<150 м запаса» работает, полное вето включается
  только при необязательном поле старта `route_top_m`. Пока оно не задано, вето
  не висит в строке «не проверено» (иначе её начали бы пролистывать ровно тогда,
  когда там окажется настоящий пробел), а показывается разовой подсказкой.
- **W\*** — у open-meteo нет потока тепла. Оценка Дира из пограничного слоя и
  радиации, доля явного тепла 0,30, погрешность порядка двойки. → везде помечена
  как оценка, одна никогда не определяет категорию.
- **B/S ratio, BL Max Up/Down, cloud streets, конвергенция** — параметры RASP,
  у open-meteo их нет. Не имитируем.
- **Молнии** — `lightning_potential` и `thunderstorm_probability` у open-meteo
  для Кавказа null на всех моделях (существуют только для ICON-D2 в Центральной
  Европе). У Blitzortung нет публичного REST API: только неофициальный
  MQTT/websocket, и политика требует от сторонних приложений своего релей-сервера.
  → молнии не делаем.

## Покрытие данных по моделям (проверено живыми запросами 25.07.2026)

ECMWF отдаёт null для `boundary_layer_height`, `lifted_index`,
`convective_inhibition`, `visibility`, ветра на 80/120 м и 950 гПа — на нём не
могут сработать 4 вето из 13. ICON молчит про пограничный слой и Lifted Index.
Полный набор дают только `gfs_seamless` и `best_match`. Отсюда смена дефолта.

## Радар RainViewer — покрытия над текущим стартом нет

Слой покрытия (`/v2/coverage/0/256/{z}/{x}/{y}/0/0_0.png`, зумы 4–7; на 8+
альфа-градиент, бинарный порог там врёт) — обратная маска: прозрачный пиксель =
радар есть. Смысл подтверждён контрольными точками: Мюнхен и Париж прозрачны,
Сахара и середина Атлантики непрозрачны.

Результат по Грузии: **Тбилиси, Гудаури, Телави, Местиа, Батуми — покрыты;
Лалискури (42.089, 45.401) лежит за краем покрытия.** Граница проходит по
диагонали примерно в 10–20 км юго-западнее старта.

Решение о том, делать ли фичу, — за пользователем: на текущем сохранённом старте
она была бы пустой, на остальных грузинских стартах работала бы.
