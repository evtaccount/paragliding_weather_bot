# Повтор запроса по упавшему старту на вкладке «Все старты»

## Задача

На вкладке «Все старты» старты, чей недельный запрос упал, перечислены одной
строкой через запятую («Не удалось получить: Laliskuri, Mestia, Racha,
Udzilaurta. Открой старт вручную, чтобы повторить запрос») — то есть экран
называет отказ и тут же отправляет пилота решать его вручную на другом экране.
Вместо перечисления — строка-кнопка на каждый старт; тап повторяет запрос
ИМЕННО этого старта.

## Почему повтора всего скана не будет

`forecast.scan_week` берёт недельные данные каждого старта по ключу кэша
`(name, "week", None, model)` (`forecast.py:86`) — по тому же ключу, что и
`GET /api/forecast?site=X&range=week` (`forecast.py:_ensure`). Значит одиночный
запрос по упавшему старту это и есть повтор того самого запроса, который скан
не смог сделать, а не какой-то другой. Второй запрос (`/api/scan` целиком)
после него не нужен ни для данных, ни для правильности: у сервера один тяжёлый
слот на пилота (`api.py:one_at_a_time`), и тратить его на повторный обход всей
библиотеки ради уже полученного ответа незачем.

## Что делаем

### 1. `OverviewDayButton` — общая кнопка дня (Overview.tsx)

Разметка дня из `RangeView` выносится в отдельный компонент: та же форма ответа
(`ForecastOverview.days_daytime`) теперь читается в двух местах — на
диапазонных вкладках и в группе перезапрошенного старта.

`flyTag` («лётно / не лётно») остаётся только у диапазонных вкладок: там в
списке лежат ВСЕ дни. В группе перезапрошенного старта нелётных дней нет по
построению, и подпись под каждым баллом ничего не сообщала бы.

### 2. `FailedSite` — строка упавшего старта (Overview.tsx)

Собственный компонент на строку, потому что запрос живёт в хуке, а хук нельзя
звать в цикле по динамическому списку.

Запрос: `useForecast(name, "week", null, model, retrying)`, где `retrying` —
состояние, поднимаемое тапом. До тапа запроса нет.

Состояния:

| состояние | что видно |
|---|---|
| до тапа | кнопка: имя старта + «Повторить» |
| запрос летит | имя старта + спиннер |
| успех, есть лётные дни | обычная группа старта: шапка «имя · румб · N лётных» + дни; тап по дню зовёт `onOpenDay(name, date)` |
| успех, лётных дней нет | «На неделе не нашлось ни одного лётного дня» — тот же вердикт, что домен положил бы в `empty` |
| отказ | имя старта + `ErrorBox` (он сам прячет «Повторить» на 4xx) |

Лётные дни отбираются по `day.assessment.flyable` — тот же серверный флаг
(`criteria.flyable`), которым домен отбирает дни в скане. Копии порога в
приложении не заводится (та же причина, что у `flyTag`: финальное ревью ветки,
I2).

Румб — `compass(overview.site.aspect_deg)`, как в шапках групп скана
(`aspect_deg` — ГРАДУСЫ, C1б).

Имя старта стоит в КАЖДОМ состоянии, включая отказ: упавших стартов бывает
несколько, и `ErrorBox` сам по себе не говорит, чей запрос не прошёл.

### 3. Блок `failed` в `ScanView`

`.empty`-плашка с перечислением через запятую заменяется на шапку
«Не удалось получить» + `FailedSite` на каждое имя.

### 4. Стили (styles.css)

`.failed` (отступ блока строки) и `.retryrow` (сама строка-кнопка: имя слева,
«Повторить» справа) — в том же виде, что и остальные карточки экрана,
переменными темы, без литералов цвета.

## Тесты (webapp/src/screens/Overview.test.tsx)

1. Упавшие старты — кнопки, по одной на старт (не перечисление через запятую).
2. Тап шлёт РОВНО ОДИН `/api/forecast?site=<имя>&range=week` и ни одного
   повторного `/api/scan`.
3. Успех показывает лётные дни этого старта; нелётные в группу не попадают.
4. Тап по дню перезапрошенного старта несёт имя ЭТОГО старта (та же проверка,
   что уже стоит на группах скана).
5. Успех без лётных дней объясняется словами, а не пустой группой.
6. Отказ повтора показывает имя старта и «Повторить».
7. Тап по одному упавшему старту не трогает соседний.
