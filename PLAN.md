# Критерии XC-полётов: единый источник порогов, почасовой скоринг 0–100, расширенные данные

## Context

Пользователь принёс исследовательский документ
(`~/Downloads/compass_artifact_wf-d22e6567-8afb-562b-9064-cfd9256c3946_text_markdown.md`) —
систему критериев погоды для горных полётов на параплане, калиброванную под уверенного
XC-пилота на Niviuk Ikuma 3 P (trim ≈38 км/ч ≈ 10,6 м/с): 6-уровневая шкала по ~18 параметрам,
9 правил вето, детерминированный скоринг 0–100 с весами и мультипликативными штрафами,
точные имена полей open-meteo, промпт для LLM.

Бот сейчас устроен беднее и вдвое жёстче документа:
- пороги — 9 констант в `engine.py:77-86` (>7 м/с уже нелётно против 10,6 м/с у документа);
- оценка дня — эвристика на 4 параметрах (`day_status`/`day_score`, `engine.py:298-327`);
- из «тяжёлых» полей запрашиваются только `cape` и `boundary_layer_height`;
- те же числа продублированы литералами в `charts.py:112-116, 281-286, 374` и пересказаны
  текстом в промпте `analysis.py:65` — при любой правке порогов карточка, полоса на
  метеограмме и промпт разъезжаются, и ни один тест этого не поймает.

Цель: перенести систему документа в бота — один источник порогов на весь проект, почасовой
скоринг с вето и лимитирующим фактором, расширенный набор полей open-meteo, честная работа
на неполных данных.

## Решения пользователя (заданы явно в этой сессии)

1. Пороги — из документа (XC-калибровка), а не текущие консервативные.
2. Скоринг — полный почасовой: субоценки → веса → штрафы → вето → категория.
3. Балл дня — **среднее по часам термического окна**.
4. Модель по умолчанию — **Auto (`best_match`)** вместо ECMWF.
5. В карточке на день — **полоса по часам** (час / эмодзи / балл) + лимитирующий фактор.
6. Нау-каст — **только радар RainViewer**, и **сначала проверить, есть ли покрытие** над
   стартом; молнии не делаем (у Blitzortung нет публичного REST API — только неофициальный
   MQTT/websocket, их политика требует своего релей-сервера).
7. Отдельно — поискать погодные сервисы (в т.ч. платные) с полным набором полей.

## Чего из документа НЕЛЬЗЯ посчитать честно (и что вместо этого)

1. **Фён по правилу Шамони** (перепад давления через хребет >4 гПа) — нужны две точки по разные
   стороны хребта. Кольцо ±0,05° в `forecast._detail_context` (`forecast.py:110`) — это ~5,5 км,
   не хребет. → **эвристическое предупреждение, не вето**: сильный ветер на 850 гПа поперёк
   экспозиции + большой спред T−Td + низкая влажность + мало низкой облачности. В коде, карточке
   и промпте помечено как эвристика.
2. **«База ниже старта»** — LCL считается по T/Td самого старта, то есть по построению никогда
   не окажется ниже старта. Реальная проверка — против **вершин маршрута**, которых бот не знает.
   → бэнд «<150 м запаса» из документа работает; полноценное вето включается только если у старта
   появится необязательное поле `route_top_m`.
3. **W\*** — у open-meteo нет потока тепла. Считаем оценку Дира из `boundary_layer_height` +
   `shortwave_radiation`; погрешность порядка ×2. → всегда печатается с «≈», помечается
   `estimate:w_star`, и одна только она никогда не определяет категорию.
4. **B/S ratio, BL Max Up/Down, cloud streets, конвергенция** — параметры RASP, у open-meteo их нет.
   Не имитируем и в скоринг не включаем.
5. **Радиус до грозовой ячейки / гэст-фронт** — только нау-каст, не прогноз.
6. **Молнии** — внешнего источника с приемлемой лицензией не нашлось (см. решение 6).

## Этап 1 — `criteria.py`: единственный источник чисел

Чистый модуль без I/O и без импорта `engine` (значения на вход → оценки на выход).

- `TRIM_MS = 10.6`, `GLIDER = "Niviuk Ikuma 3 P"`, `CRITERIA_VERSION` — версия таблицы,
  попадает в карточку и в данные для LLM, чтобы скриншот в Telegram был отслеживаемым.
- `PARAMS: dict[str, Param]` — ~18 параметров документа. Интервальная форма нужна потому, что
  часть параметров немонотонна (W\*, Thermal Index, спред T−Td, облачность, глубина ПС имеют
  оптимум в середине): у W\* уровень «отличная» — это `((1,7; 2,0), (3,0; 3,5))`.
- `GROUPS: dict[str, Group]` — 10 групп с весами документа (ветер 0,22 · порывы 0,15 ·
  направление 0,12 · термичка 0,15 · грозы 0,12 · облачность 0,08 · осадки/видимость 0,06 ·
  shear 0,06 · температура 0,02 · доп. 0,02) и объявленным способом свёртки `min`/`mean`.
- `GRADE_SCORE` = ideal 100 / excellent 85 / fair 65 / marginal 40 / no_fly 15 / danger 0.
- `CATEGORIES` — 🟢🟢 85–100 · 🟢 70–84 · 🟡 55–69 · 🟠 40–54 · 🔴 15–39 · ⛔ 0–14.
- `PENALTIES` — ×0,80 (ветер >7,8 м/с **и** W\* >3,5), ×0,85 (рассогласование направления по
  высотам в ПС >45°), ×0,85 (запас под базой <300 м при активной термичке).
- `VETOES` — 9 правил части 1.2, у каждого объявлен список нужных входов `needs` (см. этап 4).
- `RAIN_DAY_MM = 0.2`, `RAIN_HR_MM = 0.1`, `LCL_M_PER_C = 122` — константы, которые сейчас
  живут литералами в двух-трёх местах.

Публичный API:
- `grade_of(param, value) -> str | None`
- `score_hour(raw: dict) -> HourAssessment`
- `score_day(hours, window) -> DayAssessment`
- `category_of(score) -> (key, emoji, label_ru)`
- `flyable(assessment) -> bool` — категория ≥ `fair`
- `reference_text() -> str` — **генерирует** русский блок порогов, который сейчас захардкожен
  в `analysis.py:65`
- `legend(param) -> list[(grade, label)]` — для легенд графиков

Презентация остаётся снаружи: `grade_of` возвращает **имя уровня**, а сопоставление
уровень → цвет живёт в `charts.py` (`GRADE_RGB`), чтобы RGB-кортежи не переехали в модуль
критериев.

При импорте (и в тестах) проверяется самосогласованность: сумма весов = 1,0; интервалы каждого
параметра не пересекаются и покрывают всю числовую ось.

**Структура почасовой оценки** (`HourAssessment`, сериализуется в JSON для кэша и для Gemini):
`hour, score, category, emoji, label, limiting, params{value,grade,sub}, groups, weights_used,
confidence, penalties[], vetoes[], unchecked_vetoes[], warnings[], raw{}`.

**Свёртка дня** (`DayAssessment`): `date, hours[], window, score` (среднее по окну),
`category/emoji/label, best_window, limiting` (самый частый лимит-фактор окна),
`confidence` (минимум по окну), `warnings` (объединение без повторов).

## Этап 4 — правило пропусков и перенормировка

Алгоритм `criteria.score_hour`:
1. Параметры со значением `None` не оцениваются → `warnings += "no_data:<field>"`.
2. Субоценка группы = `min`/`mean` (по объявлению группы) по **присутствующим** параметрам;
   группа без единого параметра выбрасывается.
3. Веса перенормируются на выживших; `confidence` = сумма исходных весов выживших групп.
4. Взвешенная сумма → базовый балл.
5. Штрафы: применяется только тот, чьи входы не null (у остальных уже есть `no_data`).
6. Вето: для каждого сначала проверяется список `needs`. Любой null → `unchecked_vetoes`,
   вето не срабатывает. Сработавшее → `score = 0`, категория `danger`.
7. `confidence < 0,6` → категория ограничивается сверху `fair` + `warning:"low_confidence"`.
8. Ни одной выжившей группы → `score = None`, категория `no_data`, эмодзи ⚪.

Карточка и данные для LLM обязаны показывать `unchecked_vetoes` словами — «не проверено вето:
видимость, сдвиг у земли». Это главное, что отличает честную деградацию от молчаливой.
