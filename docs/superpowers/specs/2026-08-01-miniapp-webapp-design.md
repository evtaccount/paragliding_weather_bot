# Мини-приложение: интерфейс — дизайн

**Дата:** 2026-08-01
**Фаза:** 4 из спеки [2026-07-28-miniapp-architecture-design.md](2026-07-28-miniapp-architecture-design.md)

## Цель

Перенести макет `miniapp/prototype.html` в работающее приложение на Vite и React
поверх готового HTTP-слоя. После фазы пилот открывает кнопку меню в Telegram и
получает всё, что сегодня доступно командами чата, — без переписки с ботом.

## Что уже есть

Фаза 3 закончена и раскатана: `api.py` отдаёт четырнадцать эндпоинтов, подпись
`initData` проверена живым клиентом Telegram, Caddy держит TLS с автоматическим
сертификатом. Дописывать бэкенд под интерфейс не придётся — числа для всех
экранов уже отдаются.

`miniapp/prototype.html` — кликабельный макет всех экранов и шторок. Он остаётся
справочником по вёрстке и решениям и не собирается в приложение.

## Границы фазы

Полный паритет с макетом: четыре экрана и десять шторок целиком. Фаза не
считается закрытой, пока часть интерфейса существует только в макете.

Два места, где макет намеренно упрощён, здесь закрываются по-настоящему:
рельеф под маршрутом рисовался генеративно (тап по нему давал бессмысленные
координаты) и форм ввода не было вовсе.

## 1. Стек

**TypeScript.** Четырнадцать эндпоинтов с вложенными ответами; типы контракта —
единственный способ не получить `undefined` в шаблоне через два экрана после
ошибки. Бэкенд описан моделями pydantic, фронтенд отвечает тем же.

**Leaflet, не MapLibre.** Тайлы растровые (OpenStreetMap), а MapLibre заточен под
векторные: его преимущество не работает, вес и сложность остаются.

**TanStack Query для серверных данных.** Запросы к прогнозу идут в open-meteo и
Gemini и занимают секунды, API отвечает 429 на второй параллельный запрос того
же пилота, шторки открываются и закрываются помногу раз. Кэш, дедупликация и
разделение состояний «грузится / ошибка / есть данные» иначе пишутся руками в
десяти местах.

**Графики свои, на SVG, без библиотеки.** Полоса часов и столб воздуха —
придуманные под задачу представления, их нет ни в одной библиотеке; Recharts или
visx пришлось бы переламывать. Метеограмма и разрез маршрута — линии и заливки,
где библиотека не экономит почти ничего.

**Telegram через `window.Telegram.WebApp` напрямую**, с тонкой типизированной
обёрткой. Нужны `initData`, тема, кнопка «назад», разворот на весь экран и
вибро; официальный SDK добавил бы зависимость со своим темпом версий ради этого
набора.

Новые зависимости целиком: React, Vite, TypeScript, Leaflet, TanStack Query,
Vitest, Testing Library, Playwright.

## 2. Раскладка проекта

```
webapp/
  index.html
  package.json  tsconfig.json  vite.config.ts  playwright.config.ts
  src/
    main.tsx           провайдеры, тема, инициализация Telegram
    App.tsx            шапка, активный экран, таб-бар, стек шторок
    telegram.ts        обёртка над window.Telegram.WebApp
    api/
      types.ts         типы ответов API
      client.ts        fetch с подписью, перевод кодов ошибок
      queries.ts       хуки TanStack Query по эндпоинтам
      queue.ts         очередь тяжёлых запросов (см. раздел 4)
    screens/           Forecast · Overview · Route · Settings
    sheets/            десять шторок, файл на каждую
    charts/            HourStrip · AirColumn · Meteogram · RouteProfile · palette.ts
    map/               MapView на Leaflet, работа с точками
    ui/                Sheet · Chip · Row · Spinner · ErrorBox
    format.ts          числа, даты, ветер, единицы
```

Каждый файл отвечает за одно и читается целиком.

**Навигация без роутера.** Четыре вкладки — состояние, а не URL: ссылками внутрь
мини-приложения никто не делится, а react-router принёс бы историю, которой не на
что отображаться. Шторки живут стеком; кнопка «назад» Telegram снимает верхнюю, а
на голом экране закрывает приложение — её штатное поведение.

**Контекст в шапке.** Старт, дата и модель видны всегда, тело перерисовывается
под ними. Возврат к прогнозу не создаёт новое сообщение — это и есть ответ на
«в чате история быстро засоряется».

## 3. Экраны и шторки

Диапазоны прогноза в API: `1d`, `3d`, `week`, `2weeks`. Ключи моделей: `auto`,
`ecmwf`, `gfs`, `icon` — список с подписями приезжает вместе с настройками.

| Экран | Что заменяет | Эндпоинты |
|---|---|---|
| Прогноз | `/today`, `/tomorrow`, выбор дня из обзора | `GET /api/forecast` (`range=1d`) |
| Обзор | `/threedays`, `/week`, `/twoweeks`, `/scan` | `GET /api/forecast` (`3d`/`week`/`2weeks`), `GET /api/scan` |
| Маршрут | `/route`, `/saveroute`, `/routes` | `POST /api/route`, `GET·POST·DELETE /api/routes` |
| Настройки | `/model`, `/settings`, `/sites`, `/add`, `/removesite` | `GET·PATCH /api/prefs`, `GET·POST·DELETE /api/sites` |

| Шторка | Эндпоинт |
|---|---|
| Ветер по высотам | `GET /api/forecast/wind-grid` |
| Метеограмма | данные экрана прогноза, без запроса |
| Разбор дня | `POST /api/analysis` |
| Карточка точки маршрута | данные ответа маршрута, без запроса |
| Разбор маршрута | `POST /api/route/analysis` |
| Выбор старта | `GET /api/sites` |
| Выбор модели | список из `GET /api/prefs` |
| Сохранённые маршруты | `GET /api/routes` |
| Новый маршрут | `POST /api/route/parse`, карта, `POST /api/routes` |
| Добавление старта | `POST /api/elevation`, `POST /api/sites` |

**Разовая и постоянная модель разделены явно.** Чип в шапке показывает, чем
посчитан текущий экран, и подписан «разово», когда расходится с постоянной
настройкой. Про потолок отдельной строкой сказано, что он всегда по GFS.

**Причина ограничения вытесняет описание погоды.** В строках обзора и скана обе
не помещаются; «ограничивает: порывистость» полезнее, чем «переменная
облачность».

## 4. Слой данных

**Подпись на каждом запросе.** `client.ts` вешает заголовок
`Authorization: tma <initData>` из Telegram. Сессий нет — как и на сервере.

**Коды переводятся в состояния интерфейса:**

| Код | Что показывает приложение |
|---|---|
| 401 | «Откройте приложение из Telegram» |
| 403 | «Доступ по списку» и Telegram ID пилота, чтобы переслать владельцу |
| 429 | «Уже считаю» с кнопкой повтора |
| 502 | «open-meteo недоступна» с кнопкой повтора |
| 400 | текст ошибки от сервера как есть — он написан для пилота |

**Автоматических повторов нет.** Каждый тяжёлый запрос — поход в open-meteo или
Gemini; повтор по таймеру удваивал бы расход квоты незаметно для пилота. Повтор
только кнопкой.

**Клиент сам не создаёт 429.** Сервер разрешает один тяжёлый запрос на пилота
(`api.one_at_a_time`), и открытая во время расчёта шторка получила бы отказ.
Тяжёлые запросы на клиенте идут через одну очередь: второй ждёт первого. Правило
остаётся серверным, клиент просто перестаёт в него биться.

Тяжёлые — те, что на сервере висят на `one_at_a_time`: прогноз, сетка ветра,
скан, разбор, маршрут, разбор маршрута, высота точки. Настройки, списки стартов и
маршрутов идут мимо очереди: запереть их вместе с прогнозом значит подвесить весь
экран из-за одного графика.

**Кэш согласован с серверным.** Данные считаются свежими 5 минут при серверных
15 (`CACHE_TTL_MIN`): повторное открытие шторки не ходит в сеть, обновление по
требованию доступно кнопкой.

## 5. Карта и тайлы

Карта настоящая и участвует во вводе: тап ставит точку маршрута, перетаскивание
двигает, тап выбирает координаты нового старта. Показывает маршрут, точки и
старты из библиотеки.

**Тайлы проксируются через свой Caddy.** В `Caddyfile` добавляется `handle
/tiles/*` с проксированием на OpenStreetMap и заголовком `User-Agent`,
называющим приложение, — этого требуют правила использования их тайлов. Чужой
сервис видит только сервер, а не устройства пилотов, и у приложения остаётся
один источник для всего.

**Серверного кэша тайлов не будет.** У Caddy кэш не встроен: для него нужен
отдельный модуль и своя сборка образа. Тайлы кэшируются браузером по заголовкам
OpenStreetMap — это и есть основная экономия. Приватность, ради которой прокси и
выбран, сохраняется полностью.

## 6. Графики и палитра

Четыре представления:

- **Полоса часов** — время по горизонтали, высота столбика равна баллу, цвет
  берётся из шкалы лётности.
- **Столб воздуха** — рельеф, старт, рабочий коридор, потолок, база облаков по
  вертикали.
- **Метеограмма** — температура, ветер, порывы линиями.
- **Разрез маршрута** — рельеф заливкой, точки маршрута поверх.

Балл дня стоит рядом мелко: пилот летает окно, а не число. Два прибора вместо
одной карточки с большой цифрой — решение макета, оно сохраняется.

**Палитра — единственное место, где знание раздваивается.** Цвета живут в
`charts.py` (`GRADE_RGB`, `TERRAIN`, `BAND`, `TEMP`, `WIND`, `GUST`), а нужны в
TypeScript. Копия неизбежна, незаметное расхождение — нет: питоновский тест
читает `webapp/src/charts/palette.ts` и сверяет значения с константами модуля.
Разъедутся — упадёт тест, а не глаз пилота через месяц.

Цвета рядов графиков держатся отдельно от шкалы лётности: путать «жёлтый —
удовлетворительно» и «жёлтый — такая-то температура» нельзя.

## 7. Сборка и раскатка

**Статику отдаёт pgbot, а не Caddy.** Отдельный этап сборки на Node собирает
`webapp/` и кладёт результат в образ; FastAPI отдаёт его тем же `StaticFiles`,
который сейчас держит заглушку. За Caddy остаются TLS, сжатие, тайлы и
проксирование: и `/`, и `/api/*` уходят в pgbot.

Причина — Caddy отдельный контейнер и в файловую систему образа pgbot не
заглядывает. Общий том, наполняемый при сборке, был бы вторым местом, где
собранное приложение расходится с кодом. README уже предупреждает про эту
ловушку: `api.STATIC_DIR` и монтирование `./static:/srv/www` сегодня указывают в
одно место двумя способами. После фазы остаётся один.

Меняются: `Dockerfile` (этап сборки на Node), `api.STATIC_DIR` (на `webapp/dist`),
`docker-compose.yml` (монтирование статики уходит), `Caddyfile` (статика
проксируется в pgbot, добавляется `/tiles/*`), `.dockerignore` (`node_modules`).

**Заглушка уходит.** `static/index.html` сделал свою работу — подпись проверена
живым клиентом.

## 8. Проверка

**Vitest и Testing Library** — чистая логика (форматы, шкалы, разбор ответов,
очередь тяжёлых запросов) и экраны поверх замоканного API. Идут в `make test`
вместе с питоновскими: один прогон на весь проект.

**Playwright** — сквозные сценарии в настоящем браузере поверх живого `app.py` с
тестовым токеном и временной базой. Отдельная цель `make e2e`, чтобы быстрый цикл
оставался быстрым.

**Питоновский тест палитры** — сверка `palette.ts` с `charts.py`, см. раздел 6.

Что проверяется глазами и не автоматизируется: вёрстка в настоящем клиенте
Telegram в обеих темах.

## 9. Разработка без Telegram

Скрипт выпускает подписанную `initData` вашим `BOT_TOKEN` и кладёт в переменную
окружения для `vite dev` и для Playwright.

Сервер при этом не меняется ни на строку: никаких обходов проверки подписи в
продакшене — та же подпись, просто выпущенная локально. Живёт сутки и потом
перевыпускается, потому что сервер отвергает просроченные (`webauth.MAX_AGE_SEC`).

## Вне рамок

- Кнопка меню в BotFather — это фаза 5.
- Пуш-уведомления по расписанию.
- Работа приложения без сети.
- Серверный кэш тайлов (нужен отдельный модуль Caddy).

## Открытые риски

**Размер фазы.** Четыре экрана и десять шторок — самый большой кусок проекта.
Задачи плана нарезаются так, чтобы каждая заканчивалась собираемым приложением;
порядок — каркас, экран прогноза, обзор, маршрут, настройки, формы ввода.

**Тайлы OpenStreetMap** отдаются по правилам, рассчитанным на умеренную нагрузку.
Для списка допущенных пилотов этого достаточно; при росте — платный сервис с
ключом на сервере, клиент менять не придётся, он ходит в свой домен.
