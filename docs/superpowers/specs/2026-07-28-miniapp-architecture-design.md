# Telegram Mini App поверх бота — дизайн архитектуры

**Дата:** 2026-07-28
**Ветка:** `feature/miniapp-architecture`
**Макет:** [`miniapp/prototype.html`](../../../miniapp/prototype.html) (смержен в master, коммит `ba3e721`)

## Задача

Дать боту второй интерфейс — Telegram Mini App — с полным набором возможностей.
Причина: в чате история быстро разрастается, ориентироваться в ней тяжело, а в
приложении содержимое просто перерисовывается на месте.

Макет уже сделан и принят как основа. Эта спека — про то, как под него подвести
код.

## Согласованные решения

Приняты в диалоге до написания спеки. Здесь перечислены вместе с ценой, чтобы к
ним не возвращаться.

| Решение | Цена, принятая осознанно |
|---|---|
| **Обе поверхности полные.** Бот сохраняет весь набор команд, приложение повторяет его целиком | Два интерфейса к одной логике навсегда; `charts.py` и текстовые рендереры (~1100 строк) живут дальше |
| **Старты — общая библиотека.** Видят и правят все | Нет разделения «мой старт / чужой старт» |
| **Маршруты, скорость, учёт ветра, модель — личные** | Миграция: общие маршруты раздаются копией каждому |
| **SQLite** вместо JSON-файлов | Появляется схема и миграция |
| **Vite + React** для фронтенда | Node в Python-репозитории, отдельная стадия в Dockerfile |
| **Один процесс** — aiogram и FastAPI в общем asyncio-loop | Падение API роняет и бота |
| **Python остаётся.** Переписывание на Go отклонено | См. «Почему не Go» ниже |

### Почему не Go

Рассматривалось отдельно, отклонено. Go дал бы статический бинарник (образ ~150 МБ → ~20)
и типизацию вместо словарей `facts`. Против:

- **92 вызова `round()`** в домене. Python округляет половину к чётному
  (`round(84.5) == 84`), Go — от нуля (`math.Round(84.5) == 85`). Пороги категорий
  стоят на 85/70/55/40/15. Расхождение молчаливое: тесты на Go писались бы уже под
  новое поведение.
- **67 вызовов рисования Pillow** в `charts.py` — кириллица, фолбэк шрифтов,
  суперсэмплинг ×2. Визуальная регрессия почти неизбежна.
- **749 тестов** переписываются; через границу языка они страховкой не работают.
- Решение «обе поверхности полные» **максимизирует** объём порта: `bot.py` +
  `charts.py` + текстовые рендереры — ~2300 строк, существующих только ради чата.

Производительности здесь нет вовсе: задержку определяют round-trip'ы к open-meteo.
Точка возврата к вопросу — если чат когда-нибудь ужмётся до уведомлений.

## 1. Процесс и модули

Один контейнер, один процесс. Точка входа `app.py`:

```python
await asyncio.gather(
    dp.start_polling(bot),      # aiogram, как сейчас
    uvicorn_server.serve(),     # FastAPI на 127.0.0.1:8080
)
```

Наружу смотрит Caddy: TLS от Let's Encrypt, статика `webapp/dist`, проксирование
`/api/*` на uvicorn. Бот остаётся на long polling — вебхук добавил бы связанности
без выгоды.

**Почему один процесс.** `_fcache` и `_rcache` процессные, и на них построены
«Ветер по высотам» (переиспользует тёплый кэш 1d) и «Разбор» (берёт готовые
`facts`). Разделение на два сервиса удвоило бы запросы к open-meteo и убило
переиспользование кэша между поверхностями — единственную оптимизацию, которая в
проекте уже есть.

### Раскладка

```
Домен — логика не меняется
  criteria.py    скоринг и вето
  route.py       геометрия, физика, текстовый рендер для чата
  charts.py      PNG для чата
  analysis.py    Gemini
  engine.py      метеорасчёты, URL, текстовый рендер для чата
  forecast.py    фетч, кэш, оркестрация

Новое
  app.py         точка входа: polling + uvicorn
  store.py       SQLite — единственный модуль с SQL и user_id
  api.py         FastAPI — эндпоинты и валидация initData
  webapp/        Vite + React

Адаптеры
  bot.py         хендлеры aiogram
  guards.py      whitelist и throttle для чата
```

**Зависимости:** `store` не зависит ни от кого. `engine` перестаёт зависеть от
хранилища. `forecast` зависит от `engine`, `route`, `criteria`, `analysis`.
`bot` и `api` зависят от `forecast` и `store`. Циклов нет.

### Попутная чистка, без которой вариант не собирается

`engine.py` (1149 строк) держит и метеорасчёты, и хранилище. Пока чтение файлов
сидит внутри `engine`, у него нет способа узнать, чьи настройки читать.

Переезжает в `store.py`: `load_sites`, `find_site`, `add_site`, `remove_site`,
`ensure_sites_file`, `get_model_key`, `set_model_key`, константы `SITES` и
`MODEL_FILE`. Удаляются `settings.py` (57 строк) и `routes.py` (72 строки) —
их роль забирает `store.py`.

Остальные функции `engine` уже принимают `site` словарём параметром, так что
после переезда модуль становится чистыми расчётами и рендерингом.
`engine.main()` (CLI) импортирует `store` напрямую.

**Новые зависимости:** `fastapi`, `uvicorn`. `sqlite3` — из стандартной библиотеки.

## 2. Данные

`store.py` — единственный модуль, где есть SQL и `user_id`.

### Схема

```sql
-- Общая библиотека. Имя остаётся идентичностью: на нём построены ключи
-- кэша (_resolve) и callback_data, менять это ни к чему.
CREATE TABLE sites (
  name        TEXT PRIMARY KEY,
  lat         REAL NOT NULL,
  lon         REAL NOT NULL,
  elevation_m INTEGER NOT NULL,
  aspect      TEXT,          -- свободная метка; см. примечание ниже
  aspect_deg  REAL,          -- источник истины; NULL = экспозиция неизвестна,
                             -- тогда вердикт по направлению ветра пропускается
  slope_deg   REAL,          -- NULL → engine.SLOPE_DEG
  route_top_m INTEGER,       -- вершины у старта; NULL отключает вето «база ниже вершин»
  notes       TEXT,
  added_by    INTEGER,       -- Telegram user_id того, кто завёл
  added_at    TEXT NOT NULL  -- ISO-8601
);

CREATE TABLE site_aliases (
  alias TEXT PRIMARY KEY,    -- в нижнем регистре
  name  TEXT NOT NULL REFERENCES sites(name) ON DELETE CASCADE
);

-- Личное
-- Имена колонок повторяют ключи settings.DEFAULTS, чтобы переименования не было
CREATE TABLE user_prefs (
  user_id                 INTEGER PRIMARY KEY,
  avg_route_speed_kmh     REAL    NOT NULL DEFAULT 25.0,
  wind_correction_enabled INTEGER NOT NULL DEFAULT 1,   -- 0/1
  model_key               TEXT    NOT NULL DEFAULT 'auto'
);

CREATE TABLE routes (
  user_id  INTEGER NOT NULL,
  name     TEXT    NOT NULL,
  points   TEXT    NOT NULL,   -- JSON [[lat, lon, name], ...]
  saved_at TEXT    NOT NULL,
  PRIMARY KEY (user_id, name)
);

-- Переживает рестарт впервые
CREATE TABLE terrain (         -- рельеф не меняется никогда
  grid_key   TEXT PRIMARY KEY, -- от округлённых координат сетки
  elevations TEXT NOT NULL,    -- JSON-массив высот
  fetched_at TEXT NOT NULL
);

CREATE TABLE adhoc_points (    -- точки «по координатам»
  name        TEXT PRIMARY KEY,   -- "42.0893, 45.4012"
  lat         REAL NOT NULL,
  lon         REAL NOT NULL,
  elevation_m INTEGER NOT NULL,
  created_at  TEXT NOT NULL
);
```

Геометрия маршрута лежит JSON-строкой намеренно: запросов по отдельным точкам нет,
таблица точек была бы схемой ради схемы.

`adhoc_points` общие, не по пользователям: имя — это координаты, оно уникально
глобально, и двум пилотам незачем держать две одинаковые строки.

**Про `aspect` и `aspect_deg`.** Строка `aspect` фактически не читается кодом:
и расчёты, и подпись в карточке идут от `aspect_deg` через `engine.card()`.
Подтверждается расхождением, которое сейчас никого не ломает — в боевом
`sites.json` лежит латинское `"S"`, в тестовом наборе кириллическое `"Ю"`.
Колонка сохраняется как введённая пользователем метка, но источником истины
остаётся `aspect_deg`; при вводе `aspect` парсится в градусы через
`engine.parse_aspect`, и дальше живут они.

**Про `added_by`.** Ни один экран его пока не показывает. Колонка заводится
сразу, потому что восстановить задним числом, кто завёл старт, будет уже
невозможно, а в общей библиотеке с несколькими редакторами это первое, что
спросят.

### Что чинится попутно

- **Рельеф** сейчас живёт в `_terrain_cache` (кап 64) и теряется при каждом
  рестарте, хотя неизменен и стоит отдельного запроса к Elevation API.
- **Точки по координатам** тоже умирают при рестарте — настолько, что для этого
  написано отдельное сообщение пользователю в `forecast.py:176`. С базой оба
  случая исчезают; сообщение остаётся только для по-настоящему неизвестного имени.

### Обслуживание

- `adhoc_points` старше 30 дней удаляются при старте.
- `terrain` не ограничивается: строка — сотня целых, роста бояться нечего.

### Миграция при первом старте

1. Нет файла БД → создать схему.
2. Есть `sites.json` → перелить в `sites` + `site_aliases`. Поле `aliases`
   раскладывается по строкам, приводится к нижнему регистру. Ключ `_comment`
   игнорируется.
3. Есть `routes.json` → маршруты были общими, становятся личными. **Копия каждому
   из `ALLOWED_USER_IDS`.** При пустом `ALLOWED_USER_IDS` (открытый режим)
   маршруты не переносятся, а файл остаётся на месте с записью в лог — иначе
   непонятно, кому их отдавать.
4. Есть `settings.json` / `model.json` → значения становятся дефолтами для
   `user_prefs`, создаваемых при миграции.
5. Перенесённые файлы переименовываются в `*.migrated`, не удаляются.

Повторный запуск ничего не дублирует: миграция срабатывает только при отсутствии
файла БД.

### Доступ

Один процесс, два конкурента внутри — бот и API. SQLite в режиме WAL, соединение
на операцию. Записи редкие (настройка, маршрут), чтения короткие. Синхронный
`sqlite3` в asyncio-loop здесь не проблема: счёт идёт на доли миллисекунды.
Если станет заметно — обёртка в `asyncio.to_thread` внутри `store.py`, снаружи
ничего не меняется.

`user_prefs` создаётся лениво при первом обращении. Новый пилот ничего не
регистрирует: видит общие старты, настройки — дефолтные.

### Переменные окружения

Исчезают: `SITES_FILE`, `MODEL_FILE`, `SETTINGS_FILE`, `ROUTES_FILE`.
Появляется: `DB_PATH` (по умолчанию `/app/data/pgbot.db`).

### В базу не кладём

`_fcache`, `_acache`, `_rcache` — TTL 15 минут, диск им незачем.
Токены маршрутов `bot._route_cache` остаются в памяти: они нужны только чату,
где обходят 64-байтный лимит `callback_data`. Приложению они не нужны.

## 3. API и авторизация

### Валидация `initData` на каждом запросе

Клиент шлёт заголовок `Authorization: tma <initData>`. Сервер проверяет:

```
secret = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)
hash   = HMAC_SHA256(key=secret, msg=data_check_string)
```

`data_check_string` — пары `key=value`, отсортированные по ключу, без `hash`,
склеенные через `\n`. Дополнительно: `auth_date` старше суток отклоняется.

Дальше `user.id` из `initData` проходит через тот же `ALLOWED_USER_IDS`, что и бот.

Сессионных токенов нет: обмен `initData` на JWT добавил бы жизненный цикл токена
ради ничего — HMAC считается за микросекунды.

### Эндпоинты

Строятся по домену, а не по командам бота.

```
GET    /api/sites                    общая библиотека
POST   /api/sites                    добавить
DELETE /api/sites/{name}
POST   /api/elevation                высота по координатам (для формы добавления)

GET    /api/forecast                 ?site=&range=&date=&model=
GET    /api/forecast/wind-grid       ?site=&date=&model=
GET    /api/scan                     лётные дни по всем стартам
POST   /api/analysis                 разбор дня от Gemini

POST   /api/route                    профиль: {points, name, date, departure}
POST   /api/route/parse              GPX / KML / текст → точки
POST   /api/route/analysis           разбор маршрута

GET|POST|DELETE /api/routes          личные сохранённые
GET|PATCH       /api/prefs           скорость, учёт ветра, модель
```

PNG-эндпоинтов нет: приложение рисует графики само, `charts.py` остаётся чату.

`model` в query — разовый выбор (кнопка модели под прогнозом). При отсутствии
берётся `prefs.model_key`.

### Единый источник чисел

Найдено при проектировании: `report_1day` и `facts_1day` выбирают час пика
**по-разному**.

```python
# engine.py:793  (карточка для чата)
tmax_i = max(workable or day, key=lambda i: (round(temp[i],1), -abs(hour_of(t[i]) - ref)))
# engine.py:1002 (факты для Gemini)
tmax_i = max(day, key=lambda i: temp[i])
```

Профиль ветра, уходящий в Gemini, может быть посчитан для другого часа, чем «пик»
в карточке. Сейчас расхождение видно только при сверке текста с промптом; с
третьим потребителем тех же чисел оно вылезет наружу.

**Решение:** `facts_*` становятся единственным источником, `report_*` рендерят
текст из них и ничего не пересчитывают. Из `report_1day` в факты переезжают:

- `fly_dir` — направление ветра в рабочее окно (11–16, взвешенное по скорости)
- вердикт по направлению (`dir_verdict` → «в лоб» / «боковой» / «в спину»)
- список оговорок (голубая термичка, низкий потолок, фён, экспозиция, грид)

Приложению они тоже нужны, а сейчас существуют только внутри строки.

### Ошибки

| Ситуация | Код |
|---|---|
| `initData` не проходит проверку или отсутствует | 401 |
| Пользователь не в `ALLOWED_USER_IDS` | 403 |
| Старт не найден | 404 |
| `ForecastError` — плохой диапазон, дата вне горизонта | 400, текст как есть |
| open-meteo или Elevation недоступны | 502 |
| Запрос этого пользователя уже выполняется | 429 |

Тексты `ForecastError` уже написаны для человека и отдаются без перевода.

### Троттлинг

Для API — **только in-flight, без паузы**. В `guards.py` уже зафиксировано, почему
нажатия кнопок пропускают cooldown: это продолжение уже выданного результата, а не
спам. Приложение — сплошное такое продолжение, и 10-секундная пауза сделала бы его
сломанным. Гарантия «один запрос на пользователя за раз» остаётся, повторы гасит
кэш с TTL 15 минут.

## 4. Изменения в домене и боте

**Правило:** домен не знает про пользователя. Предпочтения резолвит адаптер и
передаёт параметром.

### Сигнатуры

```python
# было                                       # стало
get_forecast(site, rng, date, model=None)    get_forecast(site, rng, date, model)
get_wind_grid(site, date, model=None)        get_wind_grid(site, date, model)
get_route(points, name, date, departure_h)   get_route(points, name, date, departure_h, cfg, model)
get_analysis(site, rng, date, deep, ...)     get_analysis(site, rng, date, deep, model)
scan_week()                                  scan_week(model)
```

Новая публичная функция:

```python
async def get_facts(site_name, rng, date, model) -> dict
```

Зовёт `_ensure` и отдаёт `derived["facts"]`.

Удаляются все шесть неявных `model or get_model_key()` внутри `engine`:
`build_url` (221), `ceiling_url` (240), `_model_note` (406) и далее. Забыть
передать модель станет ошибкой вызова, а не тихим падением на глобалку.

`get_route` сейчас модель вообще не принимает и молча берёт глобальную через
`_ensure_route_weather`. После правки маршрут считается моделью пользователя.

`get_route` также перестаёт звать `settings.get()` внутри (`forecast.py:670`) —
`cfg` приходит параметром.

### Кэш хранит сырьё, а не результат

`_fetch_build` при каждом промахе рендерит 2–3 PNG через Pillow — и рендерил бы их
на каждый запрос из приложения, где они не нужны.

```python
# было:  ключ → (expires, card, pngs, facts, fallback, rows, grid)
# стало: ключ → (expires, data, assessment, derived)
#        derived = {} , заполняется лениво: card, pngs, facts, fallback, rows, grid
```

Чат просит `card` и `pngs`, приложение — `facts`, каждый платит только за своё.
Повторный запрос по-прежнему бесплатен: посчитанное оседает в `derived`.
`assess_day` считается ровно один раз на запись кэша — как и задумано
комментарием в `forecast.py:300`.

Ключ кэша не меняется: `(site_name, rng, date, model)`.

### `bot.py`

Правка механическая, около 15 хендлеров:

```python
uid   = message.from_user.id
prefs = store.prefs(uid)
card, pngs = await forecast.get_forecast(site, rng, date, model=prefs.model_key)
```

`store.prefs(uid)` возвращает замороженный dataclass с полями
`avg_route_speed_kmh`, `wind_correction_enabled`, `model_key` — не словарь:
обращения к нему рассыпаны по обоим адаптерам, и опечатка в ключе должна быть
видна сразу. Он же передаётся в `get_route` как `cfg`.

Имена полей совпадают с ключами нынешнего `settings.DEFAULTS`, поэтому
переименования не происходит — меняется только способ обращения. Восемь мест
переходят с `cfg["…"]` на `cfg.…`: `forecast.py` 606, 621, 728, 729 и `bot.py`
475, 477, 486, 487.

Кнопка разовой модели работает как сейчас: `mf|` несёт ключ, хендлер передаёт его
вместо `prefs.model_key`. `/model` пишет `store.set_model(uid, key)`, настройки —
`store.set_speed(uid, …)` и `store.set_wind_correction(uid, …)`, маршруты —
`store.routes_*(uid, …)`.

### `api.py`

То же самое, источник `uid` другой:

```python
@router.get("/forecast")
async def get_forecast(user=Depends(current_user), site: str = ..., range: str = ...,
                       date: str | None = None, model: str | None = None):
    prefs = store.prefs(user.id)
    return await forecast.get_facts(site, range, date, model or prefs.model_key)
```

## 6. Порядок работ

| Фаза | Что | Состояние после |
|---|---|---|
| 1 | `store.py` + миграция; хранилище уезжает из `engine`, `settings.py` и `routes.py` удаляются | Бот работает как раньше, но у каждого своё. Деплоится. |
| 2 | Явные `model` / `cfg`, единый источник чисел, ленивый кэш | Поведение не меняется, правка внутренняя |
| 3 | `app.py`, `api.py`, `initData`, Caddy в compose | Проверяется `curl`, приложения ещё нет |
| 4 | `webapp/` — прототип переносится в Vite + React | Приложение работает, кнопки в BotFather ещё нет |
| 5 | BotFather: домен и кнопка меню | Пилоты видят приложение |

После каждой фазы тесты зелёные и бот жив.

Фаза 1 — единственная с миграцией данных. Файлы переименовываются в `*.migrated`,
а не удаляются, поэтому откат — вернуть имена и откатить образ.

Фаза 2 меняет сигнатуры домена, но не поведение: тесты, кроме перечисленных выше,
должны пройти без правок. Если какой-то доменный тест позеленел иначе — это сигнал,
что поведение всё-таки уехало.

### Планы пишутся по фазам, а не одним куском

Объём слишком велик для одного плана реализации, и фазы разнородны:

- **Фазы 1–2** — бэкенд-рефакторинг, связаны общей правкой домена; один план.
- **Фаза 3** — HTTP-слой и инфраструктура; отдельный план.
- **Фаза 4** — фронтенд-проект на React; отдельный план, и до него имеет смысл
  вернуться к макету: часть экранов там намеренно упрощена (карта рисуется
  генеративно, форм ввода нет).
- **Фаза 5** — настройка в BotFather, плана не требует.

Спека одна на всё, потому что решения в ней сквозные; дробится реализация.
