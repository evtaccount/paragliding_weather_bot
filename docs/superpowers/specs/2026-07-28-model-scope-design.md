# Область действия выбора метеомодели — дизайн

**Дата:** 2026-07-28
**Ветка:** `feature/model-scope`

## Запрос пользователя

1. Для потолка всегда использовать GFS.
2. Кнопка выбора модели под прогнозом меняет модель только для одного запроса.
   Глобально модель меняется исключительно отдельной командой.

## Эмпирическая проверка (open-meteo, 2026-07-28)

Что какая модель реально отдаёт (запрос по координатам 42.5, 44.0):

| модель | `boundary_layer_height` | `freezing_level_height` | `lifted_index` | `convective_inhibition` | `visibility` | ветер 80/120 м |
|---|---|---|---|---|---|---|
| `best_match` | есть | есть | есть | есть | есть | есть |
| `ecmwf_ifs025` | нет | нет | нет | нет | нет | нет |
| `gfs_seamless` | есть | есть | есть | есть | есть | есть |
| `icon_seamless` | нет | есть | нет | есть | есть | есть |

Комментарий в `engine.py` о пробелах ECMWF и ICON подтверждён.

Совместимость серий для подстановки проверена отдельно: узкий запрос за
`boundary_layer_height` с `models=gfs_seamless` возвращает **тот же массив `time`**,
что и основной запрос, — для одного дня (24 значения), для обзора `forecast_days=7`
(168 значений) и для мультиточечного маршрутного запроса. Совпадают также
`timezone`, `utc_offset_seconds` и `elevation`: высота приходит из DEM open-meteo,
а не из модели. Значит подстановка — прямое присваивание по индексу, без
интерполяции по времени.

## Зачем пинить потолок на GFS

Причин две, и вторая не сводится к первой:

1. **Данных нет.** У ECMWF и ICON `boundary_layer_height` отсутствует полностью,
   поэтому потолок термиков, график потолка, `w_star`, рабочий коридор маршрута и
   критерии по пограничному слою на этих моделях отключаются.
2. **Под `auto` потолок недетерминирован.** `best_match` сам выбирает подложку по
   региону, и какая модель дала `boundary_layer_height`, из ответа не видно. Пин на
   GFS делает число воспроизводимым и сравнимым между стартами и днями.

Осознанно принимаемый побочный эффект: в карточке потолок будет из GFS, а
температура и ветер рядом — из выбранной модели. Физически это слегка
рассогласованный набор; практически потолок и так грубая оценка по глубине
пограничного слоя, а альтернатива — не показывать его вовсе.

## Часть 1. Потолок всегда по GFS

### Что именно берём

**Только `boundary_layer_height`.** Остальные пробелы выбранной модели
(`freezing_level_height`, `lifted_index`, `visibility`, ветер 80/120 м) не
заполняются: подмена половины входов скоринга чужой моделью обессмыслила бы сам
выбор ECMWF. Всё, что считается из `boundary_layer_height` — число потолка,
`w_star`, рабочий коридор, график потолка, критерии по пограничному слою —
оживает само, потому что читает уже подставленную серию.

### Механика

Второй, узкий запрос к open-meteo только за `boundary_layer_height` с
`models=gfs_seamless`, запускается конкурентно с основным через `asyncio.gather`,
поэтому задержка не растёт. Полученная серия замещает то, что вернула выбранная
модель.

`engine.py` — сборка URL рядом с существующими `build_url` / `route_weather_url`:

```python
CEILING_MODEL_KEY = "gfs"   # потолок всегда считается по этой модели
CEILING_VAR = "boundary_layer_height"
```

- `ceiling_url(site, rng, date=None)` — те же `start_date`/`end_date` или
  `forecast_days`, `timezone=auto`, `hourly=boundary_layer_height`,
  `models=gfs_seamless`.
- `route_ceiling_url(coords, date, tz)` — мультиточечный аналог с явным `tz`
  (по той же причине, что и `route_weather_url`: `timezone=auto` дал бы точкам на
  разных сторонах границы поясов разные часы).

`forecast.py` — подстановка в двух местах:

- `_fetch_build` — карточка дня и обзор;
- `_ensure_route_weather` — мультиточечный маршрут. Без этого «потолок» на
  маршруте и на старте считался бы по разным моделям.

Общий помощник:

```python
def _splice_ceiling(body, gfs_body):
    """Подставить GFS-серию пограничного слоя. True, если подстановка прошла."""
```

### Защита от порчи данных

Подстановка выполняется **только** если массивы `time` совпали. Побочный запрос
упал, вернул `error`, отдал другое число точек в мультиточечном ответе или другой
`time` — молча остаёмся на серии основной модели, то есть на сегодняшнем
поведении, плюс `log.warning`. Побочный запрос не имеет права уронить прогноз.

Когда выбранная модель уже `gfs` — второго запроса не делаем. Под `auto` запрос
делаем: это ровно тот случай, ради которого нужен пин.

### Честность в выводе

Строка карточки в `report_1day`

```
📍 42.5, 44.0 · 2640 м · Asia/Tbilisi · ECMWF
```

становится

```
📍 42.5, 44.0 · 2640 м · Asia/Tbilisi · ECMWF (потолок GFS)
```

Суффикс появляется только когда подстановка реально прошла и выбранная модель не
`gfs`. То же значение уходит в `facts_1day` → `facts["site"]["model"]`, иначе
ИИ-разбор будет утверждать, что потолок ECMWF-овский, а ECMWF его не считает.

Обзорные диапазоны модель в тексте не показывают ни сейчас, ни после изменения —
их индикатор это галочка в ряду кнопок моделей. Не расширяем.

## Часть 2. Разовый выбор модели

### Что меняется по сути

`cb_switch_model` перестаёт вызывать `engine.set_model_key`. Модель никуда не
записывается — она едет параметром через один запрос. Глобально её меняют только
`/model` и его кнопки (`md|`). Обработка `OSError` при записи `model.json` из
`cb_switch_model` уходит вместе с записью.

### Проброс модели

Явным необязательным параметром, а не неявным состоянием. Ключ кэша обязан
совпадать с URL запроса; при `contextvars` рассинхрон между ними был бы тихим
багом, а явный параметр ломает тест сразу.

`engine.py`:

- `build_url(site, rng, date=None, model=None)` → `model_id(model or get_model_key())`
- `route_weather_url(coords, date, tz, model=None)` → то же

`forecast.py` — параметр `model=None` прокидывается по цепочке:

- `_resolve(site_name, rng, date, model=None)` → четвёртый элемент ключа кэша
  становится `model or engine.get_model_key()`
- `_fetch_build(site, rng, date, model)` → `_ensure(site, rng, date, key, model)`
- публичные точки входа: `get_forecast`, `get_wind_grid`, `get_analysis`,
  `cached_dates`
- `_detail_context(site, date, model)` — запрос предыдущего дня для глубокого
  разбора должен идти на той же модели, что и сам разбор

`bot.py`:

- `send_forecast(message, site, rng, date=None, model=None)` — прокидывает модель
  и в `get_forecast`, и во все клавиатуры, которые строит

### Подпись модели на данных, а не в параметре

`report_1day` и `facts_1day` подписывают карточку меткой модели. Пробрасывать в
них ещё один параметр не нужно: метка описывает конкретный ответ, поэтому едет
вместе с ним. `_fetch_build` штампует в `data` два служебных ключа:

```python
data["_model_key"]     = model or engine.get_model_key()
data["_ceiling_model"] = engine.CEILING_MODEL_KEY   # только если подстановка прошла
```

Ведущее подчёркивание не может столкнуться с полем open-meteo. `engine` читает их
через один помощник `_model_note(data)`, возвращающий `"ECMWF (потолок GFS)"` или
`"GFS"`, с откатом на `get_model_key()`, если штампа нет (прямые вызовы из тестов
и CLI).

### Кодирование модели в кнопках

Модель кодируется одним символом явной таблицей в `engine.py`:

```python
MODEL_CODES = {"auto": "a", "ecmwf": "e", "gfs": "g", "icon": "i"}
```

Именно таблицей, а не «первой буквой ключа»: пятая модель с конфликтующей буквой
должна падать на тесте, а не тихо переключать пользователя на чужую модель.

Код дописывается последним полем **только когда разовый выбор есть**, поэтому
обычный путь остаётся байт-в-байт как сегодня и запас в лимите 64 байта не
теряется:

| было | стало при разовом выборе |
|---|---|
| `llm\|<старт>\|<диапазон>\|<дата>` | `…\|<дата>\|e` |
| `deep\|<старт>\|<диапазон>\|<дата>` | `…\|<дата>\|e` |
| `wg\|<старт>\|<дата>` | `…\|<дата>\|e` |
| `pd\|<старт>\|<дата>` | `…\|<дата>\|e` |
| `mf\|<ключ>\|<старт>\|<диапазон>\|<дата>` | без изменений — ключ уже внутри |

Цена — 2 байта, примерно один кириллический символ запаса в имени старта.

**Разбор.** Обработчики сейчас используют `split("|", N)` с ограничением, из-за
чего последнее поле поглотило бы дописанный код. Переходим на полный
`split("|")` с разбором по позициям и необязательным последним элементом. Это
безопасно: текущий разбор с `maxsplit` и так ломается на имени старта с символом
`|`, то есть запрет на `|` в именах уже действует де-факто.

`pd|` приходит из двух мест — постраничный выбор дня под обзором и результаты
`/scan`. У `/scan` разового выбора нет, код не дописывается, поэтому разбор
опирается на число полей, а не на источник.

### Что видит пользователь

Галочка переезжает на показанную модель, а не на глобальную, и подпись говорит,
что выбор разовый:

- без разового выбора: `🌐 Другая модель (разово):`
- с разовым: `🌐 Модель: ECMWF — разово. Постоянная: Auto (/model)`

Всплывающий ответ на нажатие: `ECMWF — разово, пересчитываю…`

`_model_switch_keyboard(site, rng, date, current)` получает эффективную модель
явным аргументом вместо чтения `engine.get_model_key()` внутри.

### Кэш

Модель уже входит в ключ `_fcache` / `_acache` / `_rcache`, поэтому разовый
рендер кладёт свою запись и глобальную не трогает. ИИ-разбор и ветер по высотам,
нажатые следом, попадают в тёплый кэш той же модели.

## Крайние случаи

- Побочный GFS-запрос упал или отдал несовпадающий `time` → потолок считается по
  выбранной модели, то есть на ECMWF/ICON его по-прежнему нет. Прогноз выдаётся.
- Мультиточечный GFS-ответ вернул другое число точек → подстановки нет ни в одной
  точке (частичная подстановка молча смешала бы модели по участкам маршрута).
- Разовый выбор на обзорном диапазоне → работает так же; модель видна по галочке.
- Имя старта настолько длинное, что кнопка с кодом не влезает в 64 байта →
  существующее поведение `_btn`: кнопка пропускается с предупреждением в лог.
- Нажатие кнопки модели на сообщении, где разовый выбор уже активен → просто
  новый разовый выбор; глобальная модель не меняется никогда.
- Устаревшее сообщение с кодом несуществующей модели → неизвестный код
  трактуется как «разового выбора нет», работает глобальная модель.

## Вне рамок

- Маршрутный диалог (`rt|`, `rr|`) и `/scan` разовый выбор не получают — там нет
  кнопки моделей, они и дальше идут на глобальной модели. Часть 1 (потолок из
  GFS) на маршрут при этом распространяется.
- Модель на пользователя: настройка остаётся общей, как `sites.json`.
- Заполнение из GFS остальных пробелов ECMWF и ICON.
- Показ модели в тексте обзорных диапазонов.
