# Дизайн: `/scan` — лётные дни на неделю по всем стартам

**Дата:** 2026-07-24
**Ветка:** `feature/scan-flyable-days`

## Задача

Команда, которая собирает недельный прогноз по **всем** сохранённым стартам и
показывает подходящие для полётов дни. После ответа бота пользователь может
выбрать подробный прогноз по каждому из предложенных дней (кнопки).

## Решения (продуктовые)

- **Порог «подходящего» дня:** ✅ лётный + ⚠️ с оговорками. Маргинальные и
  нелётные дни скрываем. Движок уже так классифицирует (`engine.day_status`).
- **Диапазон:** фиксированно неделя (7 дней), как в запросе. Не параметризуем (YAGNI).
- **Группировка:** по стартам.
- **Вывод:** одно длинное сообщение (текст сгруппирован по стартам) + одна общая
  inline-клавиатура.
- **Кнопки:** одна кнопка на пару (старт, день), подпись `{emoji} {день} · {старт}`,
  по одной в ряд (чтобы имя старта влезало). Нажатие → подробный прогноз на 1 день.
- **Имя команды:** `/scan`.

## Поток

1. Берём все старты через `forecast.known_sites()`.
2. Для каждого — недельный обзор через существующий `forecast._ensure(...)`
   (тёплый кэш переиспользуется; последующий `/week <старт>` бесплатен).
   Фетчи параллельно через `asyncio.gather`; упавший старт пропускаем и считаем.
3. Для каждого дня берём классификацию движка (`day_status` → ✅/⚠️/❌, `day_score`).
   Оставляем только ✅ лётный и ⚠️ с оговорками.
4. Рендер одним сообщением, сгруппированным по стартам:

   ```
   🔎 Лётные дни на неделю — по стартам

   🪂 Гудаури (Ю)
     ✅ Сб 26.07 · до 5, порыв 8 м/с · Ю · ясно
     ⚠️ Вс 27.07 · до 7, порыв 10 м/с · ЮЗ · облачно

   🪂 Юца (СВ)
     ✅ Пн 28.07 · до 4, порыв 6 м/с · СВ · ясно
   ```

   Под ним общая клавиатура: по кнопке на каждую пару (старт, день),
   подпись `✅ Сб 26.07 · Гудаури`, по одной в ряд.
5. Нажатие кнопки → подробный прогноз на 1 день. **Переиспользуем существующий
   callback `pd|<старт>|<дата>`** (`cb_pick_day`) — новый колбэк не нужен.
   В 64 байта влезает: `pd|` + имя ≤40 + `|` + дата(10) = ≤54.

## Изменения в коде

- **`engine.py`** — вынести per-day классификацию (сейчас внутри `report_overview`)
  в маленькую функцию `overview_rows(data, site, rng)`, возвращающую строки со
  статусом/score/погодой. `report_overview` вызывает её (убирает дублирование
  цикла по дням, которое сейчас продублировано в `report_overview` и `facts_overview`).
  Это то, что нужно `/scan`, чтобы видеть статус дня.
- **`forecast.py`** — `scan_week()`: по всем стартам собирает лётные дни
  (лётный + с оговорками), возвращает структуру
  `{"sites": [{"name", "aspect", "days": [row, ...]}], "failed": int, "empty": [names]}`.
  Кэш общий с `/week` (тот же `_ensure`).
- **`bot.py`** — хендлер `/scan` (флаг `forecast: True` → под кулдаун, дорогой);
  рендер сообщения + сборка общей клавиатуры (кнопки через `_btn`, callback `pd|`);
  запись в `BOT_COMMANDS` и `HELP`.

## Крайние случаи

- Нет сохранённых стартов → «Сохранённых стартов нет, добавь /add».
- Ни на одном старте нет лётных дней → «На этой неделе лётных окон нет по всем стартам».
- Старты без лётных дней в основной выдаче опускаем, упоминаем одной строкой.
- Фетч части стартов упал → отмечаем в конце («⚠️ N стартов не удалось получить»).
- Кнопка `pd|` уже защищена от прошедшей даты и устаревшего сообщения (существующие guard'ы в `cb_pick_day`).

## Тесты (в существующий `tests/test_dialogs.py`)

- `/scan` с несколькими стартами (мок недельных данных: часть дней лётные, часть нет) →
  в сообщении только лётные/с-оговорками дни, кнопки на каждую пару.
- `/scan` без сохранённых стартов → подсказка про /add.
- `/scan`, когда ни одного лётного дня → сообщение про отсутствие окон.
- Нажатие кнопки дня из scan (`pd|<старт>|<дата>`) уходит в `cb_pick_day` → подробный прогноз.

## Не делаем (YAGNI)

- Параметризацию диапазона (3d/2weeks) для scan.
- Отдельный новый callback для кнопок (переиспользуем `pd|`).
- Дневной бюджет/лимиты (whitelist + кулдаун достаточно).
