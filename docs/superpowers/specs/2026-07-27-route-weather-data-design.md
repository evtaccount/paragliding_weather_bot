# Маршрутная сводка погоды, спека 1: разбор, геометрия, погода, время — дизайн

**Дата:** 2026-07-27
**Ветка:** `feature/route-weather`
**Исходники:** `TZ_Route_Weather_Summary.md` v1.1 и `Prompt_Route_Weather_Assessment.md` v1.1 — присланы пользователем, в репозиторий не кладутся.

## Запрос пользователя

Боту скидывается маршрут полёта (массив координат или файл), он оценивает его с
точки зрения благоприятности погоды. Плюс команда настроек, в которой пока живёт
одна средняя маршрутная скорость — по ней считается, в какой момент времени пилот
окажется в каждой точке маршрута.

## Место в общей фиче

Полный объём из присланного ТЗ — это парсинг двух форматов, ресэмплинг, два внешних
API, время прибытия в двух вариантах, четыре маршрутных величины, три профиля
критериев, три вето, агрегация, скан времени вылета, обратное направление, три формата
вывода, настройки и хранение маршрутов. Для одной спеки это слишком много, поэтому
работа разрезана на три части, каждая из которых даёт работающую команду:

| Спека | Содержание | Результат для пилота |
|---|---|---|
| **1 (эта)** | разбор ввода, геометрия, рельеф, погода, время прибытия, маршрутные величины, `/settings` | фактическая таблица «километр · время · погода» |
| 2 | три профиля критериев, три маршрутных вето, агрегация, упреждающая проверка гроз, скан времени вылета, обратное направление | балл, вердикт, узкое место, лучшее время вылета |
| 3 | PNG-разрез вдоль маршрута, карточка точки, сохранённые маршруты, ИИ-разбор с валидацией | наглядность и текстовый разбор |

Первая спека сознательно заканчивается **без вердикта**. Таблица маршрутных величин
читаема сама по себе, а балл, выданный до того, как готовы профили и вето, был бы
оптимистичнее правды — ровно тот класс ошибок, против которого предостерегает §11 ТЗ.

## Согласованные продуктовые решения

- **Форматы ввода:** текст в сообщении и GPX-файл. `.xctsk` и KML не делаем.
- **Время вылета:** по умолчанию — начало термического окна в первой точке; можно
  задать вручную.
- **Горизонт:** один выбранный день за запрос, любая дата в пределах прогноза.
- **Сэмплинг:** поворотные точки включаются всегда, между ними добор с шагом,
  равным разрешению метеомодели.
- **Время прибытия корректируется на ветер** — это основной расчёт; фиксированный
  показывается справочно.
- **Настройки глобальные**, как выбор метеомодели: один файл на бота, без `user_id`.
- **Вердикт по маршруту (спека 2) — по узкому месту**, плюс отдельно «докуда долетишь».
- **Высоты в вывод не идут.** Рабочий диапазон считается и участвует в балле спеки 2,
  но в таблице его нет: пилот разбирается с высотами сам.

## Что проверено в API open-meteo

| Утверждение ТЗ | Проверка |
|---|---|
| Elevation API принимает до 100 координат за запрос | Подтверждено: «Up to 100 coordinates can be requested at once», Copernicus DEM GLO-90, разрешение 90 м |
| Forecast API принимает список координат через запятую | Подтверждено: `&latitude=52.52,48.85&longitude=13.41,2.35`, ответ становится списком структур |
| «до 1000 локаций за раз» | **Не подтверждено** — максимум в документации не указан. Поэтому потолок 50 сэмплов и разбиение на части, если API упрётся раньше |
| Мульти-точечный запрос стоит несколько единиц квоты | Подтверждено: стоимость дробная и растёт с числом переменных, периодом и числом локаций. Наши 39 переменных на один день — примерно 4 единицы на точку, маршрут из 12 точек ≈ 47 единиц из 10 000 в сутки |

## Расхождения с присланным ТЗ и как они разрешены

**Стек.** ТЗ написано под Go и Postgres: библиотеки `go-gpx`, `go-xctrack`, таблицы
`pilot_profiles` и `routes`. У нас Python и JSON-файлы. GPX разбирается штатным
`xml.etree`, настройки и маршруты живут в JSON рядом с `sites.json`. Новых
зависимостей не появляется.

**Настройки на пользователя.** ТЗ хранит их в профиле пилота. У нас настройки
глобальные — как уже сделано для метеомодели, поля `user_id` нет.

**Время прибытия.** ТЗ (§11) требует показывать фиксированное время и предупреждать
при расхождении, тумблер учёта ветра откладывает на v1.1. Пользователь выбрал
корректированный расчёт. Синтез: основной — корректированный, фиксированный
справочно, при расхождении на финише больше 20 минут — отдельная строка с обеими
цифрами. Тумблер в настройках меняет, какой считается основным; по умолчанию
включён учёт ветра (в ТЗ по умолчанию выключен).

**Шаг сэмплинга.** Первоначально предполагался шаг «час полёта». Принят довод ТЗ:
шаг равен разрешению модели, точки чаще сетки дают ложную детализацию.

**Рельеф под сэмплом.** ТЗ берёт высоту под самой точкой. Берём **максимум рельефа
по участку сэмпла** (±полшага), высоту под точкой оставляем справочной. Вопрос
пилота на переходе — перевалит ли он гребень, и решает это гребень, а не долина,
случайно оказавшаяся под точкой сетки. Цена — рабочий диапазон систематически
консервативнее при пересечении долин; это правильная сторона ошибки.

**Термическое окно.** В репозитории окно считается по геометрии солнца
(`engine.sun_hours`), в ТЗ (§4.6) — по порогам `boundary_layer_height > 500` и
`shortwave_radiation > 150`. Берётся **пересечение**: солнце задаёт астрономическую
рамку, пороги внутри неё отрезают часы, когда конвекция фактически не работает. По
отдельности каждое определение врёт в свою сторону — солнечное растягивает окно на
весь световой день, пороговое способно открыть окно в шесть утра.

**Часовой пояс.** Одноточечный код запрашивает `timezone=auto`. Для маршрута пояс
задаётся явно (переменная `TZ` бота): при `auto` каждая локация получает свой пояс,
и маршрут через границу поясов даёт точки с разными часами в одной таблице.

## Архитектура

Фича ложится на существующие слои: `bot.py` (хендлеры) → `forecast.py` (кэш и
оркестрация) → `engine.py` (запрос и производные) + новый `route.py` (геометрия).
`criteria.py` и `charts.py` в этой спеке не трогаются.

### 1. `route.py` — новый модуль

Чистая математика и парсинг. Ни сети, ни aiogram, ни глобального состояния —
тестируется целиком офлайн.

**Константы**

```python
SAMPLE_STEP_KM      = 10.0   # разрешение глобальных моделей open-meteo, 9–11 км
TERRAIN_STEP_KM     = 1.0    # шаг рельефной сетки для маршрутов от 50 км
TERRAIN_STEP_SHORT_KM = 0.5  # для маршрутов короче 50 км
TERRAIN_SHORT_KM    = 50.0   # граница, на которой переключается шаг рельефа
MAX_SAMPLES         = 50     # потолок числа погодных сэмплов
MAX_POINTS          = 50     # потолок числа точек на входе
MIN_POINTS          = 2
MAX_GPX_BYTES       = 1_048_576
MIN_WORKING_ALT_AGL = 300    # ниже этого пилот не идёт на переход, а ищет площадку
MIN_GROUND_SPEED_KMH = 8.0   # нижний порог эффективной путевой скорости
ETA_WARN_MIN        = 20     # расхождение времён прилёта, с которого предупреждаем
SITE_MATCH_KM       = 2.0    # радиус сопоставления первой точки с сохранённым стартом
PEAK_WINDOW_KM      = 5.0    # окно поиска локального максимума рельефа
```

**Разбор ввода**

```python
@dataclass(frozen=True)
class Point:
    lat: float
    lon: float
    name: str | None = None

def parse_text(text: str) -> list[Point]
def parse_gpx(data: bytes) -> tuple[list[Point], str | None]   # точки + имя маршрута
```

Правила разбора строки координат, по порядку:

1. Найти в строке все числа шаблоном `[-+]?\d{1,3}([.,]\d+)?`.
2. Ровно два числа → широта и долгота; остаток строки после второго числа →
   название точки.
3. Четыре числа, где второе и четвёртое без знака и длиной от трёх цифр →
   десятичная запятая, склеить попарно (`42,4776, 44,4787`).
4. Иначе — ошибка с номером и текстом самой строки, а не общее «неверный формат».

Дополнительно: градусы-минуты-секунды (`42°28'39"N 44°28'43"E`), вставка из Google
Maps (`42.4776,44.4787`), пропуск пустых строк и строк, начинающихся с `#`.
Однострочный компактный вид — точки через пробел.

GPX разбирается по **локальному имени тега** (пространства имён у разных экспортёров
различаются), приоритет `<rte>/<rtept>` → `<trk>/<trkseg>/<trkpt>` → `<wpt>`. Трек
прореживается сразу при разборе, до `MAX_POINTS`. Имя маршрута — из `<name>`.

**Геометрия**

```python
def haversine(a: Point, b: Point) -> tuple[float, float]   # (метры, начальный пеленг)
def resample(points, step_km, max_samples) -> list[Sample]
def terrain_grid(points, step_km) -> list[tuple[float, float]]
```

```python
@dataclass
class Sample:
    km: float                  # накопительно от старта
    lat: float
    lon: float
    name: str | None
    role: str                  # takeoff | enroute | goal
    is_turnpoint: bool
    leg_length_km: float       # длина участка, который представляет сэмпл
    track_bearing_deg: float   # пеленг i→i+1, для последнего — i−1→i
```

Правила ресэмплинга: идти вдоль ломаной, ставить сэмпл каждые `step_km`; поворотные
точки включать принудительно, даже если они ближе шага. Сумма `leg_length_km` равна
общей длине.

Взаимодействие двух потолков нужно оговорить, иначе оно разойдётся в реализации:
`MAX_POINTS` ограничивает **вход** (столько точек можно прислать), `MAX_SAMPLES` —
**выход** ресэмплинга. Поворотные точки включаются всегда, даже если их одних уже
`MAX_SAMPLES`; добор промежуточных идёт только до этого потолка. При превышении шаг
увеличивается, и фактический шаг возвращается наружу — молча прореженный маршрут
выглядел бы как полный. Требование ТЗ «минимум два сэмпла на плече» выполняется
концами плеча: короткое плечо промежуточными точками не добирается.

Шаг рельефной сетки выбирается один раз по общей длине маршрута:
`TERRAIN_STEP_SHORT_KM` для маршрутов короче `TERRAIN_SHORT_KM`, иначе
`TERRAIN_STEP_KM`.

**Рельеф**

```python
def attach_terrain(samples, grid_pts, elevations) -> None
```

Для каждого сэмпла `terrain_m` — максимум высот сетки на его участке (±полшага),
`terrain_point_m` — высота под самой точкой, `is_terrain_peak` — является ли точка
локальным максимумом в окне ±`PEAK_WINDOW_KM`.

**Погодные величины**

```python
def wind_components(speed, dir_from_deg, track_bearing_deg) -> tuple[float, float]
def cloud_base_m(terrain_m, t2m, dew2m) -> float | None
def working_band_m(cloud_base_m, terrain_m) -> float | None
```

Знаки задаются один раз и соблюдаются везде, включая промпт спеки 3:

```
θ — направление ветра, ОТКУДА дует (метеорологическое)
φ — пеленг курса, КУДА летим
wind_along = −V · cos(θ − φ)     # > 0 попутный, < 0 встречный
wind_cross = −V · sin(θ − φ)     # > 0 сносит вправо от трека
```

Проверка: ветер с запада (θ=270), курс на восток (φ=90) → `θ−φ=180`, `cos=−1`,
`wind_along=+V`, попутный. Верно.

База облаков — `terrain_m + criteria.LCL_M_PER_C * (T − Td)`. Константа берётся из
`criteria.py`, второй копии коэффициента не заводим. Рабочий диапазон —
`база − (terrain_m + MIN_WORKING_ALT_AGL)`.

**Интерполяция по времени**

```python
def interp(series, times, when) -> float | None       # линейно
def interp_dir(speeds, dirs, times, when) -> tuple    # через u/v
def worst_of_hours(series, times, when) -> float      # для осадков
```

Время прибытия почти никогда не попадает в целый час. Непрерывные величины —
линейно. Направление ветра — только через u/v-компоненты: на переходе через 0°/360°
линейная интерполяция углов даёт ошибку в сотни градусов. Осадки и вероятность
осадков — **худшее из двух соседних часов, без интерполяции**: осадки за час это
накопление, а не мгновенное значение, интерполяция размазывает ливень в морось.

**Время прибытия**

```python
def march(samples, speed_kmh, wind_at_sample, departure) -> None
```

Фиксированное время считается тривиально: `вылет + накопленный километраж / скорость`.
Основное — одним проходом вперёд. Для сегмента `i−1 → i` берётся ветер в его
середине на уже уточнённое время выхода из точки `i−1`, оттуда:

```
WCA = asin(clamp(wind_cross / Va, −1, 1))     # угол сноса
GS  = Va · cos(WCA) + wind_along              # путевая вдоль трека
GS  = max(GS, MIN_GROUND_SPEED_KMH)
```

Круговой зависимости нет: время каждой точки опирается только на уже посчитанные,
итерация до сходимости не нужна и не делается. `|wind_cross| ≥ Va` означает, что
курс не удержать — сегмент помечается флагом `crab_limited`; вето `route_no_progress`
из этого сделает спека 2.

**Термическое окно в точке**

Границы дня — `engine.sun_hours` (экспозиция склона не передаётся: в воздухе склона
нет, функция это уже поддерживает и возвращает `slope_sun_index = None`). Внутри
рамки час считается рабочим, только если `boundary_layer_height > 500` и
`shortwave_radiation > 150`. Конец окна — граница последнего рабочего часа, то есть
`close_hour + 1` в целых часах. `time_margin_min = конец окна − время прибытия`.
Если рабочих часов нет, окно `None` и запас `None` — показывается как «окно не
открывается», а не как ноль.

Отсюда же берётся время вылета по умолчанию: начало окна в первой точке. Если окно
в первой точке не открывается, автоматического времени нет — бот сообщает об этом и
просит задать время вручную. Подставлять в этом случае восход или полдень нельзя:
получилось бы правдоподобное число, за которым не стоит ничего.

### 2. `settings.py` — новый модуль

```python
SETTINGS_FILE = (os.environ.get("SETTINGS_FILE")
                 or os.path.join(os.path.dirname(engine.SITES) or ".", "settings.json"))
DEFAULTS = {"avg_route_speed_kmh": 25.0, "wind_correction_enabled": True}
SPEED_MIN, SPEED_MAX = 10.0, 45.0

```

Настройка метеомодели остаётся в `engine.py` и в эту спеку не переезжает: там она
оправдана тем, что `build_url` использует её напрямую. Маршрутные настройки такой
привязки не имеют.

Значение 25 км/ч — разумный дефолт для уверенного XC-пилота на B+. Реальный разброс:
18–22 в слабый день, 25–30 в рабочий, 30–35 у сильных пилотов на коротком маршруте.

### 3. `engine.py` — дополнения

```python
def route_weather_url(points, date, tz) -> str
def mean_wind_vector(H, i, lo_alt_msl, hi_alt_msl) -> tuple[float, float] | (None, None)
```

`route_weather_url` собирает мульти-точечный запрос: тот же набор `H_1D` и `D_1D`,
что у `/today`, одна дата, текущая метеомодель, **явный часовой пояс**. Ответ на
несколько локаций приходит списком; на одну — объектом, этот случай уже обрабатывается
в `_detail_context` и обрабатывается так же здесь.

`mean_wind_vector` — векторное среднее u/v по уровням, попадающим в слой
`[рельеф + 500 м, база облаков]`; если база не определяется — до
`рельеф + boundary_layer_height`. Уровни-кандидаты: 10, 80, 120 м над рельефом и
925, 850, 700 гПа по их геопотенциальным высотам. Уровни ниже нижней границы слоя
отбрасываются. Осреднение именно векторное: осреднение модулей завышает ветер там,
где направление разворачивается с высотой.

### 4. `forecast.py` — дополнения

```python
async def get_route(points, name, date, departure=None) -> dict
```

Порядок работы:

1. Прочитать настройки, посчитать сэмплы и рельефную сетку.
2. Рельеф — запрос к `/v1/elevation` порциями по 100 координат. Маршрут 100 км при
   шаге 1 км это 101 точка, то есть два запроса, а не один, как написано в ТЗ.
3. Погода — один мульти-точечный запрос (при упоре в лимит — несколько частей).
4. Собрать профиль маршрута.

Кэши:

- **рельеф** — без срока, рельеф не меняется. Ключ — хеш списка координат сетки,
  размер кэша ограничен.
- **погода** — ключ `(хеш точек, дата, модель)`, время жизни как у остальных
  прогнозов (`CACHE_TTL_MIN`). Скорость и тумблер ветра в ключ **не входят**: они
  влияют только на пересчёт времени, который дешёв и делается поверх кэша.

### 5. `bot.py` — дополнения

- `/route [дата] [ЧЧ:ММ]` с телом-списком координат и обработчик GPX-документа.
  Дата — `сегодня` / `завтра` / `YYYY-MM-DD`. Флаг `flags={"forecast": True}`, то
  есть тот же белый список и кулдаун, что у прогнозов.
- `/settings` — текущие значения, кнопки `20` · `25` · `30` · «ввести свою» (ввод

- Кнопок под маршрутной карточкой в этой спеке нет: «другое время вылета» осмысленно
  только вместе со сканом из спеки 2, «детали точки» — из спеки 3.

## Формат результата `get_route()`

Словарь ровно той структуры, что описана в §2 промпт-документа, минус поля скоринга.
Спека 2 дозаполняет баллы, спека 3 отдаёт этот же словарь модели — один формат на всю
фичу, а не три похожих.

```python
{
  "route": {
    "name", "date", "departure", "timezone", "total_km",
    "avg_route_speed_kmh", "wind_correction_enabled",
    "sample_step_km", "sample_count", "model",
  },
  "points": [{
    "km", "leg_length_km", "role", "lat", "lon", "name",
    "track_bearing_deg",
    "eta", "eta_fixed",
    "terrain_m", "terrain_point_m", "is_terrain_peak",
    "cloud_base_m", "working_band_m",
    "wind_along_kmh", "wind_cross_kmh",
    "wind_working_alt_kmh", "wind_working_alt_dir",
    "effective_ground_speed_kmh", "crab_limited",
    "window",              # {"open_hour": int, "close_hour": int} либо None
    "time_margin_min",     # None, если окна нет
    "site_match",          # имя сохранённого старта в радиусе 2 км, иначе None
    "weather": {...},      # переменные open-meteo на момент прибытия
  }],
  "notes": [...],          # строки о деградации: рельеф недоступен, шаг увеличен
}
```

Роли: первая точка — `takeoff`, последняя — `goal`, остальные — `enroute`. Если
первая точка совпадает с сохранённым стартом в радиусе `SITE_MATCH_KM`, её параметры
(в первую очередь экспозиция) подтягиваются в `site_match` — спека 2 использует это,
чтобы включить критерий направления к склону.

```
 20  12:04  → +10  ЗСЗ 12   2.6

 40  12:47  →   0  ЗЮЗ 14   2.7
```

```
🌧 40–60 км: осадки 0,4 мм, 13:30–15:00

⚠️ Без учёта ветра прилёт был бы
   в 14:37 — на 1ч59м раньше
📊 9 точек, шаг 10 км, модель Auto
```

Пример посчитан для курса 150° и скорости 25 км/ч: ветер отходит с северо-западного
на южный, попутная составляющая сменяется встречной, на последних двух сегментах
путевая упирается в нижний порог 8 км/ч — отсюда и разрыв между 14:37 и 16:36. Знаки
проверяются по формуле выше, времена — маршем вперёд.

- **Вдоль** — составляющая ветра вдоль курса в км/ч, стрелка попутный/встречный.
- **Ветер** — абсолютный на рабочей высоте: направление и скорость.
- **Поток** — оценка силы потоков W\* в м/с, единственная числовая характеристика
  термички, не являющаяся высотой.
- **Осадки и грозы — строками под таблицей, а не колонкой.** В колонке они дали бы
  пять прочерков в хороший день и съели ширину; строкой они называют километр и час,
  то есть отвечают на вопрос «где именно», а не «есть или нет».
- **Запас времени — одной строкой.** По точкам он меняется монотонно, интересны
  концы. Отрицательный запас на финише — то, ради чего строка существует.
- Километры накопительные от старта, время — в поясе бота.

Рабочего диапазона высот в выводе нет по прямому решению: он считается и участвует
в балле спеки 2, но пилот разбирается с высотами сам.

## Ошибки и деградация

Разбор ввода сообщает **номер и текст проблемной строки**. Отдельные сообщения на
«меньше двух точек», «больше пятидесяти», «GPX без маршрута, трека и точек», «битый
XML», «файл слишком большой».

**Рельеф не получен** — рабочий диапазон, отметка вершины и всё производное не
считаются, в профиле `None`, в карточке прямая строка «рельеф недоступен, рабочий
диапазон не посчитан». Высоту грид-ячейки из ответа прогноза вместо него **не
подставляем**: в горах ячейка 9–11 км промахивается на сотни метров, и это не
ухудшенный ответ, а неверный. Тот же принцип, по которому в проекте уже перечисляются
непроверенные вето.

Скорость вне 10–45 км/ч отклоняется с пояснением, что это средняя по маршруту с
учётом наборов, а не скорость крыла. Дата вне горизонта прогноза — ошибка с
указанием доступного диапазона. Если время прилёта выходит за пределы суток, маршрут
дальше не считается и это пишется явно: данные запрошены на один день. Отсутствие
переменной у выбранной модели — прочерк в таблице и упоминание в строке полноты, как
уже сделано для однодневной карточки.

## Тесты

Всё офлайн, сеть только в одном сборочном тесте на замоканном ответе.

**Разбор ввода.** Точка и запятая как дробный разделитель; `42,4776, 44,4787`;
вставка из Google Maps; градусы-минуты-секунды; комментарии и пустые строки;
однострочный вид; одна точка; пятьдесят одна точка; мусорная строка. GPX: `<rte>`,
`<trk>` с прореживанием, только `<wpt>`, с пространствами имён и без, битый XML,
пустой файл.

**Геометрия.** Haversine и пеленг на известных парах; пеленг через антимеридиан;
ресэмплинг — две точки на 80 км дают девять сэмплов, две тысячи точек трека дают не
больше пятидесяти, поворотные сохранены, сумма `leg_length_km` равна общей длине.

**Знаки ветра.** Восемь комбинаций «ветер × курс», в том числе запад плюс курс на
восток равно попутный положительный.

**Интерполяция.** Направление между 350° и 10° даёт 0°, а не 180°; осадки берутся
худшим из двух часов, а не средним.

**Время прибытия.** Марш вперёд при усиливающемся встречном даёт время позже
фиксированного; срабатывает нижний порог 8 км/ч; `|wind_cross| ≥ Va` помечается
флагом.

**Рабочий диапазон.** База ниже рельефа плюс 300 даёт отрицательное значение;
отсутствие рельефа даёт `None`, а не ноль; `terrain_m` сэмпла равен максимуму по
участку, а не высоте под точкой.

**Термическое окно.** Фикстура, где солнечное и пороговое определения расходятся, —
проверяется именно пересечение; отсутствие рабочих часов даёт `None`.

**Настройки.** Значение вне диапазона, испорченный файл, отсутствующий файл → дефолт
25 км/ч.

**Деградация.** Рельеф не получен → `None` и строка в `notes`; переменной нет у
модели → прочерк.

**Сборка.** `get_route()` на замоканном ответе open-meteo возвращает словарь ожидаемой
формы со всеми перечисленными полями.

## Что не входит в эту спеку

Баллы, категории, лимитирующий фактор, вето, агрегация, статус выполнимости, узкое
место, скан времени вылета, обратное направление, упреждающая проверка гроз (спека 2).
PNG-разрез, карточка точки, сохранённые маршруты и их команды, ИИ-разбор и валидация
его ответа (спека 3). Форматы `.xctsk`, строки `XCTSK:`/`XCTSKZ:`, KML. Оценка
маршрута по дням недели. Перенос настройки метеомодели в `settings.py`.

## Оговорки, которые должны попасть в комментарии кода

1. Сетка 9–11 км не разрешает долинные ветры. На маршруте по ущельям составляющая
   вдоль курса будет неверна именно там, где она важнее всего — в узких местах, где
   локальный ветер расходится с синоптическим на 90° и больше.
2. Конвергенции и облачные улицы — главные «трассы» горного кросс-кантри — на такой
   сетке невидимы полностью. Расчёт систематически недооценивает хорошие дни с
   выраженной конвергенцией.
3. Маршрут считается по прямой между точками. Реальный кросс-кантри уходит к облакам
   и вдоль хребтов, фактический путь на 10–25 % длиннее прямой, и время прибытия
   соответственно позже.
4. Средняя маршрутная скорость сама зависит от условий: в слабый день она падает, и
   оценка «долечу к 15:00» становится оптимистичной вдвойне — летишь медленнее и
   окно закрывается раньше.
5. Рельеф сэмплируется с шагом 1 км по DEM 90 м. Узкий перевал шириной 500 м может
   быть пропущен, и наоборот — острая вершина рядом с трассой может дать ложное
   срабатывание ограничения по высоте.
6. Формула базы облаков даёт базу термических кучевых и неприменима при слоистой
   облачности. На маршруте это встречается чаще, чем над одним стартом, потому что
   маршрут пересекает разные воздушные массы.
7. Время прибытия считается одним проходом вперёд: ветер сегмента берётся на момент
   выхода из предыдущей точки. При резком усилении ветра внутри сегмента время будет
   слегка занижено.
